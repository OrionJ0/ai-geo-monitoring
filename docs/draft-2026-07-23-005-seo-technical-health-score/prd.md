# SEO 技术健康评分 v4 PRD

## Problem Statement

当前单页和全站 SEO 报告使用“通过检查项权重 ÷ 全部检查项权重”的方式生成技术健康度。该算法虽然可配置、可复现，但仍把 SEO 当作一组可互相补偿的平行检查项：大量已通过的基础项可能抵消少数上游阻断或全站系统性问题，导致分数与用户感知不一致。

真实全站报告中，64 个页面共执行 1,283 个检查实例，其中 405 个失败，Meta Description、Canonical、结构化数据等问题覆盖大部分或全部页面，但旧算法仍可能得到 73 分。企业负责人难以据此判断网站是否健康，SEO 和开发人员也难以从分数理解问题为什么严重、应该先修什么。

同时，“搜索健康”会让用户误以为系统掌握真实抓取、收录、排名和流量数据；当前系统实际拥有的是 HTTP、HTML、robots、Sitemap、页面结构和爬虫权限等技术证据，只能评价网站的技术 SEO 条件。把检查通过率作为第二个主指标又会产生新的认知负担，用户会困惑应该相信健康分还是通过率。

## Solution

将现有评分升级为版本化的“技术健康分 v4”：

- 页面只展示一个主分数“技术健康分”，用于表达网站在访问与发现、索引资格、内容理解、展示与增强四个阶段中的技术风险。
- 检查数量作为检测范围事实展示，不再把检查通过率作为第二个主指标。
- 同类问题先按规则聚合，再根据受影响页面比例计算扣分，避免错误数量和网站规模直接操纵分数。
- 四个技术阶段拥有固定分值预算；规则权重只决定该规则在所属阶段中的份额。
- 确定的上游阻断触发分数封顶，不能被其他通过项抵消；证据不足时不生成误导性分数。
- 问题按照阻断状态、技术阶段、实际扣分、首页影响和覆盖率排序，并解释本次实际扣分，不预测排名、流量或收录提升。
- 单页和全站使用同一套阶段、规则、状态和阻断定义；历史报告保存评分版本并保持旧报告可读、可导出、可回导。

## User Stories

1. As an 企业负责人, I want one clear technical health score and status, so that I can quickly judge whether the website needs immediate attention.
2. As a 网站运营者, I want to see how many pages and checks were actually covered, so that I understand the evidence behind the report.
3. As an SEO 负责人, I want issues grouped by technical stage and affected-page coverage, so that systemic problems are not hidden by many passed checks.
4. As an SEO 负责人, I want crawl and index blockers to outrank presentation enhancements, so that I can arrange repairs in the correct causal order.
5. As a developer, I want every deduction to be traceable to a rule, affected pages, facts, and an explicit recommendation, so that I can verify and fix it.
6. As a returning user, I want comparable historical reports to show score and issue changes, so that I can confirm whether repairs improved technical readiness.
7. As a maintainer, I want scoring behavior versioned and constrained by invariant rules, so that configuration changes cannot silently create contradictory scores.

## Scope

- In scope:
  - 将 SEO 报告主指标统一命名为“技术健康分”，并显示“优秀 / 健康 / 需要改进 / 高风险 / 存在阻断 / 无法判断”状态。
  - 报告头部只展示一个主分数；检测页面数、检查总数、通过数、失败数和聚合问题数放入检测范围详情。
  - 把计分规则归入“访问与发现、索引资格、内容理解、展示与增强”四个阶段，阶段预算分别为 30、25、30、15 分。
  - 同类问题按规则 ID 聚合后，根据受影响页面覆盖率计算扣分；站点级问题按整站覆盖计算。
  - MVP 固定首页页面权重为 3、普通页面权重为 1，不提供任意连续页面权重配置。
  - 规则权重只决定规则在所属阶段中的分值份额；总分由四个阶段得分相加。
  - 确定的访问、robots 和索引阻断触发分数封顶，并在报告中明确展示封顶原因。
  - Sitemap 无效保持高风险问题，但不作为绝对阻断。
  - 证据不足、检测器无法完成关键验证时显示“无法判断”，不生成伪精确分数。
  - 问题按照阻断状态、技术阶段、实际扣分、首页影响和页面覆盖率排序。
  - 问题继续采用“具体问题 → 检测事实 → 修改建议”的内容结构，并新增阶段、覆盖率和本次实际扣分信息。
  - 单页和全站模式共享评分口径；单页覆盖率按当前页面计算，全站覆盖率按本次实际检测范围计算。
  - 历史报告保存评分版本、阶段得分、原始小数分、检测范围、阻断状态和问题扣分明细。
  - 现有 CSV 导出和回导继续支持新报告的完整结构化数据，不丢失阶段、覆盖率、阻断和评分版本信息。
  - 旧版报告继续按原始版本查看、导出和回导，不被 v4 静默重算。
- Out of scope:
  - 不把检查通过率作为第二个主分数或首页核心指标。
  - 不预测关键词排名、自然流量、真实收录量或任何搜索引擎官方评分。
  - 不展示“预计排名提升”“预计流量提升”或“修复后预计搜索提升”。
  - 不使用“预计分数提升 ÷ 修复成本”决定问题优先级。
  - 不引入判断可信度乘数、任意连续页面权重或站点自定义修复成本。
  - 不接入 Google Search Console、Bing Webmaster Tools、百度搜索资源平台或服务器日志。
  - 不训练机器学习评分模型，不做跨网站排行榜。
  - 不自动识别产品页、分类页、内容页等复杂页面模板。
  - 不覆盖或删除旧评分报告。
- Later:
  - 接入搜索平台真实抓取、收录和展现数据，单独形成“抓取与收录健康”和“搜索表现健康”。
  - 在拥有足够样本后校准阶段份额、阻断阈值和健康等级。
  - 识别产品页、分类页、内容页等页面类型，并在可验证的前提下扩展页面重要性模型。
  - 在技术事实与真实搜索结果建立稳定相关性后，再评估 SEO 综合健康指标。

## Product Behavior

### 术语与报告头部

- 主指标固定命名为“技术健康分”，不得使用“搜索健康分”“官方 SEO 分数”或暗示排名预测的名称。
- 完整报告头部展示：
  - 技术健康分和健康状态。
  - 主要瓶颈阶段。
  - 阻断问题数量。
  - 高风险聚合问题数量。
- 检测范围详情展示：
  - 单页或全站模式。
  - 实际检测页面数、发现页面数和页面上限。
  - 检查实例总数、通过数和失败数。
  - 聚合问题类型数量。
  - 是否达到页面上限，以及结果是否仅代表已检测范围。
- 不在报告头部并列展示检查通过率百分比。

### 四阶段评分

| 阶段 | 分值预算 | 产品含义 | 主要规则 |
| --- | ---: | --- | --- |
| 访问与发现 | 30 | 搜索及重要 AI 搜索爬虫能否访问并发现页面 | HTTP、HTTPS、robots.txt、计分爬虫权限、Sitemap、可抓取链接、响应与 HTML 体积 |
| 索引资格 | 25 | 页面是否具备进入索引的技术资格 | Meta Robots、X-Robots-Tag、Canonical |
| 内容理解 | 30 | 页面主题、层级和正文是否能被机器明确理解 | Title、Meta Description、H1、标题层级、正文深度、语言、低权重 Keywords |
| 展示与增强 | 15 | 页面是否具备移动端、图片和富结果等增强条件 | JSON-LD、Viewport、图片 Alt、Open Graph、Twitter Card |

- Google、Bing、百度验证标签继续分别展示检测事实，但不参与技术健康分；缺少验证标签不代表网站无法抓取或索引。
- 搜索引擎和 AI 搜索类爬虫权限参与评分；用户触发访问、AI 训练和数据使用类爬虫权限只展示，不参与评分。
- Sitemap 无效、为空、不可访问或没有有效 URL 时不能通过；该问题属于访问与发现阶段的高风险问题，但不触发绝对阻断封顶。

### 覆盖率与扣分

- 同一规则在同一页面只能产生一个计分结果。
- 全站报告先按规则 ID 聚合失败实例，再计算受影响页面覆盖率；不得按失败实例数量直接重复扣除完整规则分值。
- 页面级问题的加权覆盖率为：

```text
受影响页面权重 ÷ 已检测适用页面权重
```

- 首页权重固定为 3，其他页面权重固定为 1；单页模式下当前页面覆盖率为 100%。
- 站点级问题覆盖率为 100%，但同一站点级规则在一份全站报告中只计一次。
- 每条规则在所属阶段中的份额为：

```text
规则配置权重 ÷ 所属阶段全部计分规则权重
```

- 每条聚合问题的实际扣分为：

```text
阶段分值预算 × 阶段内规则份额 × 问题覆盖率
```

- 阶段得分最低为 0，最高不超过该阶段预算；四阶段得分相加得到原始技术健康分。
- 报告显示整数分，历史和比较保留原始小数分，避免连续修复因四舍五入丢失变化。

### 阻断与无法判断

- 以下确定事实触发阻断或封顶：
  - 首页确认持续无法访问或确认返回不可用状态：技术健康分最高 20。
  - robots 规则明确阻止全部主要传统搜索爬虫访问站点：技术健康分最高 20。
  - 首页明确设置 `noindex`：技术健康分最高 39。
  - 加权页面覆盖率达到或超过 50% 的页面明确禁止索引：技术健康分最高 39。
  - 加权页面覆盖率达到或超过 50% 的页面无法解析出有效正文：技术健康分最高 59。
- 同时命中多个封顶条件时使用最低上限。
- 报告必须展示触发的规则、事实、受影响范围和最终分数上限，不得只显示低分而不解释。
- 已收到明确 HTTP 状态、HTML 指令或 robots 规则属于可计分事实；DNS、网络、超时、关键文件不可读等无法区分网站故障与检测器故障的情况属于证据不足。
- 关键证据不足导致无法完成主要阶段判断时，报告状态为“无法判断”，不展示技术健康分，并提供重新检测入口和具体失败事实。
- 达到配置的页面上限不等同于检测器失败；仍可生成“基于已检测范围”的分数，但必须突出显示范围限制，不得宣称覆盖全站。

### 健康状态

| 条件 | 状态 |
| --- | --- |
| 关键证据不足，无法形成可靠判断 | 无法判断 |
| 命中确定的访问或索引阻断 | 存在阻断 |
| 未命中阻断且分数为 0–59 | 高风险 |
| 未命中阻断且分数为 60–79 | 需要改进 |
| 未命中阻断且分数为 80–89 | 健康 |
| 未命中阻断且分数为 90–100 | 优秀 |

- “存在阻断”优先于分数区间文案。
- 只要存在任何计分失败项，技术健康分不得达到 100。

### 问题列表与修复顺序

- 问题排序依次比较：
  1. 是否触发阻断。
  2. 所处阶段顺序：访问与发现 → 索引资格 → 内容理解 → 展示与增强。
  3. 本次实际扣分，从高到低。
  4. 是否影响首页。
  5. 受影响页面覆盖率，从高到低。
- 不使用配置化修复成本参与默认排序，不把低成本增强项排在上游阻断之前。
- 每个问题必须展示：
  - 检查对象和具体问题。
  - 健康状态或严重程度。
  - 所属技术阶段。
  - 受影响页面数、适用页面数和覆盖率。
  - 是否影响首页。
  - 检测事实和示例 URL。
  - 本次技术健康分扣分。
  - 小字修改建议。
- “扣分”只解释技术健康分构成，不得描述为排名、流量或收录提升。

### 历史与比较

- 新报告保存评分版本、检测模式、范围限制、四阶段得分、原始小数分、状态、封顶原因和逐问题扣分。
- 只有评分版本相同、检测模式相同且均形成有效分数的报告才展示直接分数差值。
- 历史比较同时展示：
  - 技术健康分变化。
  - 四阶段得分变化。
  - 已解决、新增和持续存在的问题。
  - 两次实际检测页面数及范围变化。
- 评分版本变化时显示明确断点，不把不同版本分数连接为连续趋势。
- 旧版历史继续显示原始分数和版本，并标记“旧版评分”；不得使用 v4 结果覆盖旧报告。

### 导出与回导

- v4 报告继续使用现有标准 CSV 导出和回导入口。
- 导出文件必须保留评分版本、技术健康状态、四阶段得分、原始分、阻断原因、问题覆盖率和实际扣分。
- 原文件回导后必须恢复相同的评分事实和展示结果，并作为当前账户的新历史保存，不覆盖原报告。
- 旧版 CSV 继续允许导入和查看，不要求补造不存在的 v4 字段。

## Acceptance Criteria

- AC-001: 单页和全站报告的主指标均显示为“技术健康分”，不再使用“搜索健康分”或暗示搜索引擎官方评分的文案。
- AC-002: 报告头部只展示一个主分数；检查总数、通过数和失败数进入检测范围详情，不并列展示第二个通过率分数。
- AC-003: v4 报告包含访问与发现 30 分、索引资格 25 分、内容理解 30 分、展示与增强 15 分四个阶段，阶段预算之和为 100。
- AC-004: 每个计分规则只能属于一个阶段；验证标签、用户触发和 AI 训练类爬虫权限可展示但不参与技术健康分。
- AC-005: 同一规则影响多个页面时按规则聚合，并使用受影响页面覆盖率计算一次扣分；同一检查不得在同一页面重复计分。
- AC-006: 首页固定权重为 3、普通页面固定权重为 1；单页模式下当前页面覆盖率为 100%。
- AC-007: Sitemap 返回 200 但为空、格式无效或没有有效 URL 时为高风险失败；该问题不单独触发阻断封顶。
- AC-008: 首页确认不可用或 robots 明确阻止全部主要传统搜索爬虫时，技术健康分不超过 20，并展示封顶事实。
- AC-009: 首页明确 `noindex`，或明确禁止索引的加权页面覆盖率达到 50% 时，技术健康分不超过 39。
- AC-010: 无有效正文的加权页面覆盖率达到 50% 时，技术健康分不超过 59。
- AC-011: 多个封顶条件同时存在时使用最低上限；其他通过项不能突破该上限。
- AC-012: 关键证据不足时状态为“无法判断”，不展示伪精确分数；达到配置页面上限时仍可显示基于已检测范围的分数和醒目范围说明。
- AC-013: 修复任意一个失败问题且其他事实不变时，分数不得下降；扩大问题覆盖率且其他事实不变时，分数不得上升。
- AC-014: 相同输入事实和评分版本必须产生相同阶段得分、原始分、整数分、状态和排序。
- AC-015: 只要存在计分失败项就不能得到 100 分；不存在失败项且证据完整时可得到 100 分。
- AC-016: 问题列表严格按照阻断、阶段、实际扣分、首页影响和覆盖率排序，不使用修复成本或预计流量决定默认顺序。
- AC-017: 每个问题展示具体问题、检测事实、覆盖率、示例页面、实际扣分和小字建议；问题标题不得使用建议性语句代替实际发现。
- AC-018: 60、80、90 分边界分别对应“需要改进、健康、优秀”；0–59 为“高风险”，确定阻断优先显示“存在阻断”。
- AC-019: 单页和全站使用相同的阶段、规则份额、状态区间和阻断定义；两种模式的差异仅来自检测范围和覆盖率。
- AC-020: 新历史报告保存评分版本、四阶段得分、原始分、范围、状态、封顶原因和问题扣分；旧版报告保持可读且不被重算。
- AC-021: 历史只在评分版本、检测模式和有效性满足可比条件时显示分数差值；版本变化时显示断点。
- AC-022: v4 CSV 导出和回导后，评分版本、阶段得分、状态、阻断、覆盖率和扣分数据保持一致；旧版 CSV 继续可导入。
- AC-023: 评分实现必须通过确定性、单调性、覆盖率方向、封顶不可抵消、无重复计分和满分条件的自动化测试。
- AC-024: 前端真实报告在桌面和窄屏下均能清楚区分主分数、检测范围、阻断事实、问题事实和修改建议。

## Metrics / Success

- 100% v4 报告的整数分可以由四阶段得分和封顶原因完整解释。
- 100% 聚合问题可追溯到受影响页面、检测事实、覆盖率和实际扣分。
- 自动化性质测试中，确定性、修复单调性、覆盖率方向和阻断封顶全部通过。
- 用户测试中，企业负责人和普通站长能在不阅读规则说明的情况下判断网站状态；SEO 和开发人员能正确指出前三项修复优先级。

## Constraints

- 技术健康分只评价本次可公开观察的技术 SEO 事实，不代表 Google、Bing、百度或任何 AI 搜索平台的官方评分。
