# DeepSeek Web 真实页面监测 PRD

状态：已完成并正式启用。

> 历史规则说明：本文最初采用“Web 预检失败时跳过 Web、其他平台继续”的规划语义。该语义已于 2026-07-29 被当前产品规则替代：手动运行、完整监测重试和自动监测在创建任务前实时检查全部所选 Web 平台，任一平台不可用即整体阻断；分析重试不检查 Web 登录。以下旧表述只保留为历史决策记录，不是当前正式行为。

## 2026-07-27 运行入口修订

品牌项目页的项目级“运行分析”入口已退役。当前手动入口统一为问题库中的单问题运行和问题集运行，两者都生成独立运行报告并拥有明确的失败重试关系；项目自动监测仍保留。本文后续如出现“项目运行”，均指复用 `ProjectRunService` 的内部执行链路，不表示品牌项目页仍存在项目级手动入口。

DeepSeek Web 成功执行后复用同一浏览器会话；浏览器连接、命令或生成超时会回收异常会话，使下一条任务重新启动 Chrome；后端关闭时关闭浏览器。登录状态保存在专用 Chrome profile 中，系统不保存账号密码。

## Problem Statement

当前系统通过 DeepSeek API 获取回答，并基于 API 返回结果完成品牌提及、竞品、情绪、排名、引用和历史趋势分析。但 API 返回不能代表用户在 DeepSeek 官方网页中最终看到的完整体验，网页可能使用不同的模型配置、系统提示、联网检索链路、账号设置和界面后处理，并展示 API 中不存在或表现不同的引用、来源卡片与推荐顺序。

系统目前缺少一个可验证的真实网页采集通道，因此无法回答以下问题：

- 同一个问题在 DeepSeek API 与 DeepSeek 官方网页中的回答是否不同。
- DeepSeek 网页是否展示了明确引用、来源卡片或不同的推荐顺序。
- 网页回答是否完整采集，联网搜索是否真实开启。
- 页面结构变化、登录失效、验证码或超时发生时，历史结果是否仍然可信。

本需求不重新建设一套 GEO 系统，也不迁移 OneGlanse 的完整技术栈。目标是在现有 `ai-geo-monitoring` 项目中补充一个最小、真实、独立且可核验的 DeepSeek Web 监测样本。

## Solution

把 DeepSeek 网页版注册为独立监测平台 `deepseek-web`，与现有 DeepSeek API 平台 `deepseek` 完全分开。

系统使用本机专用 Chrome 会话访问 DeepSeek 官方网页，由用户首次人工登录，并在本机固定浏览器目录中复用登录状态。项目运行时，系统为每个问题创建新对话、确认联网搜索状态、提交问题、等待最终回答稳定，然后保存页面可见正文、明确引用、采集元数据和截图证据。

DeepSeek Web 采集继续使用现有项目运行、问题集运行、项目自动监测、历史记录、结构化分析和报表链路。网页采集失败时返回明确失败，不调用 DeepSeek API，不生成替代回答。

第一版仅支持本机、单账号、单浏览器页面和串行采集。页面自身产生的网络请求只用于辅助判断会话、生成状态和引用候选；最终回答和明确引用必须以页面实际可见内容为准。

## User Stories

1. As an GEO 用户, I want to 将 DeepSeek 网页版作为独立平台加入项目, so that 我可以监测真实网页用户看到的回答。
2. As an GEO 用户, I want to 分别查看 DeepSeek API 和 DeepSeek Web 的记录, so that 两类样本不会在历史和平台对比中混淆。
3. As an GEO 用户, I want to 每个问题使用一个新对话, so that 前一个问题的上下文不会污染后续结果。
4. As an GEO 用户, I want to 确认每次采集确实开启了联网搜索, so that 搜索型回答具有可核验证据。
5. As an GEO 用户, I want to 查看网页最终回答、明确引用和截图, so that 我可以复核系统分析是否来自真实页面。
6. As an GEO 用户, I want to 继续使用现有品牌、竞品、情绪、排名和引用分析, so that Web 样本可以进入现有 GEO 工作流。
7. As an 运行人员, I want to 人工登录一次后复用本机会话, so that 服务重启后不需要为每个任务重新登录。
8. As an 运行人员, I want to 在登录失效、验证码、页面变化或超时时看到明确错误, so that 系统不会把不完整页面伪装成成功结果。
9. As an 系统维护者, I want to Web 任务强制串行但 API 任务保持原有并发, so that 单账号网页会话稳定且不会拖慢其他平台。
10. As an 系统维护者, I want to DeepSeek Web 失败后绝不回退到 API, so that 样本来源始终真实、可追踪。

## Scope

- In scope:
  - 新增独立平台 `deepseek-web`，显示名称为“DeepSeek 网页版”。
  - 保留 `deepseek` 作为独立的 DeepSeek API 平台。
  - 使用本机已安装的 Chrome 和独立的固定用户目录。
  - 提供 `web:login` 命令，由用户首次人工登录或重新登录。
  - 登录状态仅保存在本机专用浏览器目录中。
  - 支持问题库单问题运行、问题集运行和项目自动监测。
  - 每个问题创建一个新对话。
  - 每次提交前开启并验证联网搜索状态。
  - 等待本次回答生成结束且正文稳定。
  - 提取当前回答的页面可见正文。
  - 提取当前回答明确展示或明确关联的引用链接。
  - 保存联网状态截图和最终回答截图。
  - 保存页面 URL、采集时间、采集版本、浏览器环境、完成判据和证据文件标识。
  - Web 任务在同一后端进程内全局串行执行。
  - 将采集结果接入现有原回答、引用、品牌、竞品、情绪、排名、历史和报表链路。
  - 提供明确、可检索的 Web 采集错误码。
  - 记录删除和项目删除时同步清理对应截图。

- Out of scope:
  - 豆包、千问、腾讯混元或其他平台的 Web 采集。
  - 多账号、账号轮换或账号池。
  - 多浏览器、多页面并发或多进程 Web Worker。
  - Redis、BullMQ、ClickHouse 或新任务系统。
  - Playwright、Camoufox、代理池、自动反指纹或验证码绕过。
  - 自动注册、自动登录、自动输入密码或自动处理验证码。
  - 读取、保存或重放浏览器 Authorization、Cookie 等会话凭据。
  - 直接调用或封装 DeepSeek 网页私有接口。
  - Web 失败时回退 DeepSeek API。
  - 新建一套 Web 监测管理前端。
  - 将 `deepseek-web` 用作 AI 结构化分析平台、问题建议生成平台、模型目录来源或 API 连接测试平台。
  - 通过直接 SSE 检测入口或旧独立检测定时任务运行 `deepseek-web`。
  - 在第一版保证无人值守服务器、无桌面环境或机器休眠状态下的调度可用性。

- Later:
  - 根据真实运行证据评估其他平台 Web Adapter。
  - 根据稳定性数据评估 Playwright、Camoufox 或独立 Worker。
  - 多账号与跨进程调度。
  - Web 采集成功率、页面版本和错误趋势看板。
  - 更完整的网页结构化内容保真，包括复杂表格和富媒体。

## Product Behavior

### 1. 平台身份与样本隔离

- `deepseek` 始终表示 DeepSeek API。
- `deepseek-web` 始终表示 DeepSeek 官方网页版。
- 新建项目和问题时，DeepSeek API 与 DeepSeek Web 作为两个独立平台选项展示。
- 历史记录、问题集报告、平台筛选、指标聚合和导出必须保留各自的平台代码与名称。
- 系统不得把 `deepseek-web` 归一化为 `deepseek`，也不得把两者合并为同一平台样本。
- DeepSeek Web 的模型字段使用网页界面标识，不声明无法从页面确认的后台模型版本。

### 2. 登录与会话

- 运行人员通过本地 `web:login` 命令启动专用 Chrome。
- 用户在真实 DeepSeek 页面中人工完成登录、验证码和账号选择。
- 系统检测到可用的对话输入区域后确认登录成功。
- 命令结束后保留浏览器用户目录，后续运行和服务重启继续使用该登录状态。
- 专用用户目录不能与日常 Chrome profile 或 SEO 临时浏览器目录共用。
- 系统不要求用户复制 Token，也不读取、保存或展示 Authorization 和 Cookie。
- 登录失效后不自动尝试密码、验证码或账号恢复，必须重新人工执行登录命令。

### 3. 运行前检查

运行 `deepseek-web` 前检查：

- Chrome 可执行文件是否存在。
- 专用用户目录是否可读写且没有被其他进程占用。
- 浏览器是否可以启动并访问 DeepSeek 官方页面。
- 当前页面是否具有有效登录态。
- 当前页面结构是否与受支持的采集版本匹配。

如果运行开始前已经可以确认平台不可用：

- 明确返回不可用原因。
- 当没有其他可运行平台时，不创建等待任务且不消费检测配额。
- 历史行为（已退役）：当存在其他可运行平台时，其他平台继续运行，并明确列出被跳过的 DeepSeek Web。当前正式行为为整次运行阻断。

如果运行已经开始后才发现会话失效或页面异常，本条记录进入失败状态并保存对应失败原因。

### 4. 单次采集流程

每个问题按以下产品行为执行：

1. 等待获得全局 Web 串行执行权。
2. 打开或恢复专用 DeepSeek 页面。
3. 创建新对话，并确认没有复用上一问题的回答上下文。
4. 开启联网搜索，并读取页面状态确认已经生效。
5. 将当前问题输入页面并发送。
6. 识别发送后新出现的当前回答区域。
7. 等待回答开始生成。
8. 等待生成控件结束、回答正文非空且连续一段时间不再变化。
9. 提取当前回答区域中的可见正文和明确引用。
10. 保存联网状态证据、最终页面证据和采集元数据。
11. 将结果交给现有结构化分析和指标链路。
12. 释放串行执行权，处理下一条 Web 任务。

发送问题后不得自动重试整次操作，避免同一个问题在不同对话中重复提交。只有在问题尚未发送时，才可以恢复浏览器启动或页面导航。

### 5. 串行与任务关系

- 同一后端进程内所有 DeepSeek Web 任务共用一个先进先出的串行队列。
- 无论任务来自问题库单问题运行、问题集运行还是项目自动监测，任意时刻最多只有一个 DeepSeek Web 问题处于页面交互或采集阶段。
- DeepSeek API 和其他 API 平台继续使用现有并发设置，不必等待 Web 队列。
- 第一版只支持单个 Node.js 后端进程；检测到不受支持的多实例场景时不得宣称已经实现全局串行。
- 当出现登录失效、验证码或无法识别的页面结构时，Web 采集进入不可用状态，当前及排队任务快速失败，不重复刷新页面触发连续验证。

### 6. 回答完成与成功条件

一次 Web 采集只有同时满足以下条件才算成功：

- 发送后识别到新的当前回答区域。
- 回答正文非空。
- 页面生成状态已经结束。
- 回答正文连续稳定达到规定时间。
- 联网搜索状态已经被页面证据确认。
- 当前回答截图保存成功。
- 采集结果通过字段、长度、协议和 URL 边界校验。

只看到“停止生成”按钮消失不能单独证明回答完整。

任何必需条件失败时，本条记录不得进入成功指标，不得把页面中的旧回答、加载中文本或部分回答作为最终回答。

### 7. 引用与来源

- 只有当前回答正文中的引用标记、当前回答明确关联的来源卡片或当前回答明确展示的 HTTP/HTTPS 链接，才属于明确引用。
- 页面自身网络响应可以提供来源候选，但不能仅因为候选存在就记为明确引用。
- 能与当前页面可见引用关联的来源保存为 `explicit_citation`。
- 只在检索结果中出现、没有被当前回答明确引用的来源保存为 `retrieval_candidate`。
- 只有 `explicit_citation` 进入现有引用率、引用次数和引用来源 KPI。
- 没有明确引用是合法结果，保存空明确引用列表，不把它当成采集失败。
- 引用 URL 只接受 HTTP/HTTPS，拒绝脚本协议、浏览器内部协议和无法校验的值。

### 8. 页面网络观测

- 系统可以监听当前 DeepSeek 页面自身产生的网络事件，辅助识别会话、生成完成状态和来源候选。
- 系统不得使用观测到的 Authorization、Cookie 或其他会话凭据主动发起请求。
- 页面网络响应不能替代最终 DOM 正文和截图。
- 网络响应中的字段只有经过白名单提取、边界校验并与当前回答关联后才能进入采集结果。
- 原始认证头、完整网络响应体和无关页面请求不得写入日志、数据库或证据文件。

### 9. 证据与历史

成功记录保存：

- 页面最终可见回答正文。
- 明确引用和可区分的检索候选。
- DeepSeek 对话页面 URL。
- 采集开始、完成和截图时间。
- 采集结构版本与选择器版本。
- Chrome 版本、用户代理、语言、时区和视口。
- 页面观测到的客户端版本与平台标识。
- 联网搜索请求值、观测值和验证方式。
- 回答完成状态及稳定时间。
- 回答正文摘要哈希。
- 联网状态截图和最终回答截图的证据标识与文件哈希。

截图文件不写入数据库。数据库只保存不透明证据标识和有界元数据，不返回服务器绝对文件路径。

记录所有者和管理员可以通过现有历史详情访问对应证据；其他用户不能访问。删除普通历史记录或永久删除项目时，对应截图必须同步清理。

### 10. 与现有分析链路的关系

- 页面最终正文写入现有原回答字段。
- 页面引用按现有来源角色进入引用分析。
- 品牌、竞品、提及、推荐、排名、情绪和引用指标继续由现有分析服务生成。
- 如果 Web 采集成功但结构化分析失败，原回答、引用、截图和 Web 采集元数据必须保留。
- 已保存完整原回答时，后续失败重试可以只执行结构化分析，不重新访问 DeepSeek 页面。
- Web 采集元数据在成功、分析失败和允许保留证据的采集失败路径中均不得被终态更新覆盖。

### 11. 失败状态

第一版至少区分：

- 未配置 Chrome。
- Chrome 启动失败。
- 专用用户目录被占用。
- 登录失效或尚未登录。
- 页面要求人工验证或验证码。
- 页面结构与支持版本不匹配。
- 新对话创建失败。
- 联网搜索状态无法确认。
- 问题输入或发送失败。
- 回答生成超时。
- 回答未完整结束。
- 截图或证据保存失败。
- 浏览器意外关闭。

失败行为：

- QuestionRecord 保存明确错误阶段和错误码。
- 不创建成功的可见性指标。
- 不生成伪造回答。
- 不改用 DeepSeek API。
- 页面已产生的部分正文不得作为成功原回答供后续分析。
- 可以保存受保护的失败截图和有界诊断元数据。
- 错误提示不得包含账号、Token、Cookie、完整请求头、服务器目录或原始敏感响应。

### 12. 平台能力边界

`deepseek-web` 只提供真实页面监测能力：

- 可以参与项目、问题和问题集的平台选择。
- 可以参与问题库单问题运行、问题集运行和项目自动监测。
- 不出现在 AI 结构化分析平台候选中。
- 不提供模型目录读取。
- 不提供 API Key 编辑、显示或清除操作。
- 不执行 API 连接测试或通用联网 API 测试。
- 不被问题建议生成流程自动选择。
- 不被直接 SSE 检测入口或旧独立定时任务意外调用。

现有平台设置页面可以展示该平台的类型、启用状态和本机运行状态，但第一版不新增独立管理页面。

## Acceptance Criteria

- AC-001: 系统内同时存在 `deepseek` 和 `deepseek-web` 两个平台代码，平台名称和历史记录可以明确区分 API 与网页样本。
- AC-002: `deepseek-web` 不要求配置 API Key，也不会出现在 API Key、模型列表或 AI 结构化分析平台操作中。
- AC-003: 运行人员可以通过 `web:login` 启动专用 Chrome，并完全人工完成 DeepSeek 登录或验证。
- AC-004: 登录成功并正常关闭浏览器后，重启后端服务仍能使用同一专用用户目录恢复登录状态。
- AC-005: 专用 DeepSeek 用户目录不与用户日常 Chrome profile、SEO 临时浏览器目录或仓库受版本控制目录共用。
- AC-006: 用户可以从问题库的单问题或问题集运行入口选择 DeepSeek 网页版并创建真实 Web 监测任务。
- AC-007: 单问题运行、问题集运行和项目自动监测使用相同的 DeepSeek Web Adapter 和错误语义。
- AC-008: 连续运行两个问题时，每个问题都建立新对话，并取得不同的新对话证据，不读取前一个回答作为当前结果。
- AC-009: 每次发送问题前系统都验证联网搜索处于开启状态；无法确认时任务失败且不发送问题。
- AC-010: 成功记录必须同时保存最终可见正文、联网状态证据、最终回答截图和完整的有界采集元数据。
- AC-011: 成功条件同时验证新回答区域、正文非空、生成结束、正文稳定和截图成功，不以单一按钮状态判断完成。
- AC-012: 当前回答明确展示的引用保存为 `explicit_citation`，仅在网络响应中出现但页面未明确引用的来源不进入引用 KPI。
- AC-013: 回答没有明确引用时保存空引用列表，记录仍可在其他成功条件满足时完成。
- AC-014: DeepSeek Web 原回答可以继续生成现有品牌提及、竞品、推荐、排名、情绪和引用分析结果。
- AC-015: Web 采集成功但结构化分析失败时，原回答、引用、截图和 Web 采集元数据仍被保留，并支持仅重做分析。
- AC-016: 所有 DeepSeek Web 页面任务在单进程内严格串行，观测到的最大页面采集并发数为 1。
- AC-017: DeepSeek API 和其他 API 平台不进入 Web 串行队列，继续使用现有平台并发设置。
- AC-018: 登录失效、人工验证、页面结构变化、搜索状态无法确认、超时和截图失败均返回独立机器可读错误码。
- AC-019: 登录失效、人工验证或选择器失效后，排队中的 Web 任务快速失败，不重复刷新页面或持续触发验证。
- AC-020: 问题发送后不自动提交第二次；超时或回答不完整时记录失败，不把部分回答作为成功结果。
- AC-021: Web 失败后 DeepSeek API Adapter 调用次数为 0，系统不生成 API 替代结果。
- AC-022: 失败记录不创建成功的可见性指标，也不会产生可供结构化分析重试的伪完整回答。
- AC-023: 页面 Network 监听只观察当前页面产生的请求；系统不重放请求，不保存或使用 Authorization 和 Cookie。
- AC-024: 数据库、日志、错误响应和截图元数据中均不存在 Authorization、Cookie、完整请求头或浏览器 profile 绝对路径。
- AC-025: 截图通过不透明证据标识读取；记录所有者和管理员可以访问，其他用户被拒绝。
- AC-026: 删除普通历史记录或永久删除项目后，对应 DeepSeek Web 截图被同步清理。
- AC-027: `deepseek-web` 不会被 AI 结构化分析、问题建议生成、模型列表、直接 SSE 检测或旧独立定时任务选择。
- AC-028: 历史、筛选、问题集报告、平台对比和导出始终保留 `deepseek-web` 平台代码，不归一化或合并到 `deepseek`。
- AC-029: 真实入口验收至少包含一次人工登录、一次服务重启、一次项目运行、一次问题集运行和一次项目自动监测。
- AC-030: 实现验收通过代码搜索和测试证明不存在 DeepSeek Web 到 DeepSeek API 的 fallback、Token 环境变量或私有接口直连路径。

## Constraints

- 第一版运行环境为本机单 Node.js 后端进程、单 DeepSeek 账号和可用的桌面图形会话。
- 运行机器必须安装受支持的 Chrome，保持开机、联网且桌面用户会话可用。
- 登录状态只能保存在 DeepSeek Web 专用用户目录中。
- 浏览器自动化只复用现有 CDP 底层能力，不新增 Playwright 或 Camoufox。
- Web 任务必须使用页面真实交互，页面 Network 监听只作为辅助证据。
- 不允许通过复制 Token、Cookie 或调用私有接口替代页面交互。
- 不新增任务队列、独立 Worker 或分析数据库。
- 不为 Web 采集新增业务数据库表；截图使用本地证据存储，数据库保存有界元数据和引用。
- 不改变现有 API 平台的调用、并发和重试语义。
- DeepSeek 页面结构可能变化；系统必须通过版本化采集规则和明确失败保护数据可信度。
- 第一版不承诺无图形界面服务器、机器休眠、系统锁屏或多后端实例环境中的可用性。
