# 百度 Provider 模块化重构 PRD

## Problem Statement

当前 `BaiduMarketingClient` 在一个约 1957 行的适配器中同时承担 OAuth、账户目录、搜索推广四报表、百度统计报告，以及 allowlist、超时、响应体预算和网络错误归一。它已经承载生产真实数据，任何整理都不能改变四报表预算、限流、双读、精确值、原子快照或百度统计响应合同。

003 只负责统一 OAuth 凭据，刻意保留现有 provider，避免把凭据迁移与大型重构叠加。该选择对 003 正确，但 provider 的长期维护边界仍然不清：修改一个百度产品时需要理解另外两个产品，未来拆分还可能复制安全 HTTP 逻辑。

本需求在 003、营销 API 资源化需求 006 和生产数据正确性需求 007 全部关闭后进行纯行为保持重构。目标是缩小百度产品变化的影响范围，同时确保页面、公开 API、数据库、快照、错误和请求预算相对 007 修正后的正确基线无行为变化。

## Solution

采用最小模块化结构：

1. 保留 `BaiduMarketingClient` 的现有构造方式、方法和导出，作为项目内兼容 facade；
2. facade 内部组合 OAuth、搜索推广、百度统计三个产品客户端；
3. 三个客户端共用唯一安全 HTTP 内核，统一执行 allowlist、HTTPS、超时、响应体预算、JSON 解析和稳定网络错误；
4. 产品请求、响应校验、分页、限流和规范化继续由各产品客户端负责；
5. 先冻结拆分前黑盒特征合同，再移动实现；
6. 正式切换后删除旧单体产品逻辑，不保留双 provider、feature flag 或 fallback。

## User Stories

1. As a 后端开发人员, I want OAuth、搜索推广和百度统计具有独立模块边界, so that 修改一个产品时不会扩大到其他产品。
2. As a 安全维护人员, I want 所有百度出站请求使用同一个安全 HTTP 内核, so that allowlist、超时和响应预算不会被复制或绕过。
3. As a 测试人员, I want 拆分前后的请求、输出、错误和预算可以自动比较, so that 行为保持有证据而不是主观判断。
4. As a 运维人员, I want 重构不包含数据库或公开 API 迁移, so that 发布和恢复边界单一。
5. As a 市场负责人, I want 所有页面和指标来源保持不变, so that 后端整理不会改变已经验收的数据。

## Scope

### In scope

- 冻结现有客户端的构造、方法、请求序列、返回值和错误合同；
- 拆分 OAuth 授权、签名、Token 上游调用和账户目录；
- 拆分搜索推广计划、单元、关键词和搜索词四报表；
- 拆分百度统计站点、趋势、质量、来源和页面报告；
- 建立唯一共享安全 HTTP 内核；
- 保留现有 facade、CommonJS 导出和 provider 注入方式；
- 保持四报表 QPS、分页、请求/行数/字节/时间预算、双读和原子快照；
- 保持百度统计设备、来源、日期、分页、响应预算和错误语义；
- 增加黑盒特征、脱敏 request trace、模块边界和等价性测试；
- 从正式入口完成真实百度推广、百度统计和营销页面回归；
- 删除旧单体产品实现及失效说明。

### Out of scope

- 实施或修改 003 的 OAuth、迁移 014/015、用户名或产品状态；
- 修改 006 定义的营销公开 API、分页、前端消费者或 Dashboard 合同；
- 修改 007 定义的双周期、来源分区、页面消歧或脱敏回归合同；
- 修改数据库 schema、缓存、快照或 `refresh_run_id`；
- 修改报告类型、字段、日期、预算、限流或双读策略；
- 修改百度统计来源映射、站点绑定或页面报告语义；
- 引入官方 SDK、provider registry、通用插件系统或任务系统；
- 全面整理营销模块 composition root；
- 接入官网、53KF、线索池或销售系统；
- 支持多百度账号、多统计用户名或跨账号站点；
- 建设百度上游合同漂移监测。

### Later

无。新的产品行为、公开接口或账号模型出现真实需求后单独立项，不在本需求预留抽象。

## Product Behavior

### 1. 开始门禁

本需求只有在 003 完成 A2、006 完成 R2、007 完成生产正确性验收并全部关闭后才能实施。默认排期为 003 → 006 → 007 → 005。005 的目的不是先整理“基础架构”，而是对已经正确的外部行为做物理拆分；提前实施会把 007 已知缺陷冻结为等价基线并造成重复搬移。

### 2. 用户无感

重构前后：

- 管理员仍从同一入口完成授权并查看产品状态；
- 广告、关键词、搜索词、网站流量和市场总览继续调用当时现役 API；
- 广告事实仍来自百度推广，访问事实仍来自百度统计；
- 官网、53KF 和销售系统状态不受影响；
- 合法空值、权限、重新授权、上游故障和错误码含义不变。

若需要改变接口、字段、错误、请求次数或数据语义，应停止本需求并另立产品需求。

### 3. 模块边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| OAuth 客户端 | 授权、签名、Token 上游调用、账户目录 | 广告报告、统计报告、Token 持久化 |
| 搜索推广客户端 | 四报表、预算、限流、双读、精确值 | OAuth 刷新持久化、统计数据、数据库事务 |
| 百度统计客户端 | 站点、趋势、质量、来源、页面报告 | 广告指标、官网咨询、销售数据 |
| 安全 HTTP 内核 | allowlist、HTTPS、超时、响应预算、JSON、网络错误 | 产品字段、来源映射、业务归因 |
| 兼容 facade | 保持现有调用表面并委托 | 产品实现、fallback、第二套安全策略 |

### 4. 等价性证明

拆分前先使用脱敏 fixture 冻结：

- HTTP 方法、路径、请求顺序和脱敏请求体；
- timeout、最大响应字节、QPS 等待和 body cancel；
- 归一化数据、精确金额和四报表顺序；
- 错误类型、错误码、HTTP 状态和可重试标记；
- 服务调用和数据库原子快照结果。

拆分后同一测试原样通过。不能通过修改 golden 掩盖行为变化，也不永久保留旧实现做运行时 differential。

### 5. 正式切换

本需求不做生产双跑。完整测试通过后，一次切换到新 facade 组合并删除旧单体实现。阻断性回归只通过后代 revert revision 和正式 Git Bundle 快进恢复，不直接编辑服务器源码、不非快进回退、不增加隐藏 fallback。

## Acceptance Criteria

- AC-001：003、006 或 007 任一未关闭时，005 不进入实现。
- AC-002：现有调用方无需修改即可使用新 facade，构造、方法、返回和错误保持等价。
- AC-003：任一百度出站请求只经过一个共享安全 HTTP 内核并命中相同 allowlist、timeout 和响应预算。
- AC-004：OAuth 授权、刷新和账户目录的请求、规范化及错误不变。
- AC-005：四报表类型、顺序、QPS、分页、预算、双读和同一 `refresh_run_id` 原子快照不变。
- AC-006：百度统计站点、趋势、质量、来源和页面报告的设备、日期、分页、空值及错误不变。
- AC-007：产品客户端互不调用，也不能绕过共享内核。
- AC-008：拆分前冻结的 request trace、返回值、错误和预算测试在拆分后全部通过。
- AC-009：正式运行只有一个 facade、一个内核和每类一个产品客户端，不存在旧实现、双 provider 或 fallback。
- AC-010：公开 API、页面、数据库、缓存和来源口径变化数量为 0。
- AC-011：代码、日志、fixture、文档和 Git diff 不出现生产 Token、Secret、授权码或原始敏感响应。
- AC-012：从 `https://insight.guangtuo.com` 完成真实刷新和页面验收后，新结构才可成为唯一正式路径。

## Metrics / Success

- 旧单体文件中的产品实现数量为 0；
- 正式百度出站安全内核数量为 1；
- 公开 API、前端合同和数据库变化数量为 0；
- 拆分前后等价性测试通过率为 100%；
- 四报表请求、预算、双读和快照语义变化数量为 0；
- 百度统计合同和错误语义变化数量为 0；
- 凭据泄露事件为 0；
- 正式入口新增数据或页面回归数量为 0。

## Constraints

- 生产 Token 只存在于服务器数据库密文和服务端内存；
- 第三方响应始终视为不可信输入，并在产品边界严格校验；
- manifest 继续是正式端点、能力和预算的版本化真值；
- 不新增数据库迁移、配置、API 版本、feature flag 或第二套 transport；
- 不以减少测试或放宽校验换取文件变短；
- 单元测试通过不能代替正式入口验收；
- 正式入口和发布流程继续遵循项目部署文档。

## Open Questions

实现前重新盘点 003、006、007 完成后的 facade 方法和消费者，并以 007 修正后的来源分区、页面消歧和错误语义冻结统计 golden。若发现仓库外消费者直接依赖内部实现，应先登记真实兼容范围；不能通过长期保留整份旧实现解决。
