# 广拓市场数据监控前端信息架构方案 V2

## 一、方案定位

本项目已从单一 GEO/SEO 监测更新为**只读市场数据监控系统**。GEO/SEO 是当前正式运行的一组监控能力，不是整个项目的唯一边界。

系统最终联合观察：

```
百度广告/自然访问 → 官网落地页 → 表单/咨询 → 市场部确认 → 销售线索池 → 机会 → 订单(签订金额)
```

数据来源边界（CONTEXT.md 已确认）：

| 来源 | 读取内容 | 当前状态 |
|---|---|---|
| 百度营销 | 展现、点击、消费 | 页面入口已展示，真实数据为白名单试点 |
| 百度统计 | PV、访问次数、访客数 | 页面入口已展示，真实数据为白名单试点 |
| 官网落地页系统 | 原始咨询 | 来源系统尚无 API |
| 内部销售系统 | 订单标识 + 订单签订金额 | 来源系统尚无 API |
| 人工关联 | 订单↔咨询的归属关系 | 待上述来源接入后建立 |

销售侧只同步订单签订金额这一个结果指标。有效线索、销售机会只解释业务过程，不进入监控指标。

## 二、目标用户与首页目标

**主要用户**：广拓市场负责人。
**兼顾用户**：公司管理层。

首页 10 秒回答三个问题：
1. 最近 30 天投入和流量怎么样？
2. 当前全链路数据接到了哪里？
3. 哪些指标异常，下一步应该查看什么？

## 三、核心设计原则

1. 单公司、单品牌，不提供品牌或业务线切换。前端通过系统默认项目自动解析广拓上下文，用户不需要理解"项目"概念。
2. 系统只读，不使用暗示可修改来源数据的文案。
3. 首页展示结论，明细进入下钻页面。
4. AI 搜索和 SEO 不进入市场首页首屏，但保留完整的侧边栏入口。
5. 未接入数据标记"待接入"并注明所需来源系统，不显示零值或模拟数字。
6. 不把同期广告与网站数据描述为确定归因结果。
7. 沿用现有 Ant Design 和蓝色视觉体系，不重做整套组件库。
8. 现有营销页面（`/geo/marketing`）的百度数据和百度统计集成逻辑可复用，不推倒重写。

## 四、侧边栏信息架构

### 分组逻辑

每个分组回答一个明确问题：

| 分组 | 回答的问题 | 何时可见 |
|---|---|---|
| 市场总览 | 投入、流量、转化结果怎么样？ | 百度 VERIFIED 后可见 |
| 投放与流量 | 广告和网站访问的具体数据？ | 百度 VERIFIED 后可见 |
| 转化结果 | 咨询和订单数据？ | 首个转化来源接入后可见 |
| AI 品牌监测 | AI 平台怎么呈现我的品牌和竞品？ | 始终可见（GEO 正式工作流） |
| 网站诊断 | 官网技术 SEO 是否健康？ | 始终可见 |
| 监测任务 | 运行了哪些监测、结果如何？ | 始终可见 |
| 系统 | 通知、设置和账户 | 始终可见 |

### 侧边栏结构

```
市场总览                          ← 百度 VERIFIED 后可见，设为默认首页

投放与流量                        ← 百度 VERIFIED 后可见
├── 广告表现                      ← 对应现有营销监控的百度广告部分
└── 网站流量                      ← 对应现有营销监控的百度统计部分

转化结果                          ← 首个转化来源接入后可见
├── 原始咨询                      ← 落地页系统 API 开放后
└── 订单结果                      ← 销售系统 API 开放后

─────────────────────────────

AI 品牌监测                        ← 始终可见（GEO 正式工作流）
├── AI 搜索表现                    ← 原"项目看板"
└── 引用来源分析                   ← 原"来源分析"

网站诊断                           ← 始终可见
└── SEO 健康检测                   ← 原"SEO检测"

监测任务                           ← 始终可见
├── 问题库                         ← 保留原名
└── 运行报告                       ← 保留原名

─────────────────────────────

系统                               ← 始终可见
├── 系统通知
├── 个人中心
└── 管理设置                       ← 数据连接、账户绑定等
```

### 与上一版方案的关键差异

1. **"转化结果"独立分组**：把原始咨询和订单结果从市场总览的全链路卡片中拎出来，在侧边栏也有独立入口。这解决了上一版"概览卡片提到转化但没有对应下钻页"的问题。未接入时该分组整体隐藏，不产生死链接。

2. **"AI 品牌监测"替代"AI 品牌洞察"**：监测是系统实际做的事（采集、分析、报告），洞察暗示智能推理和建议——当前系统不做 AI 建议生成。命名应对齐实际能力。

3. **明确可见性规则**：每个分组标注了何时可见，而不是一次性全部展示。这解决了上一版"市场总览是默认首页但百度还没 VERIFIED"的矛盾——当前阶段侧边栏中 GEO 功能仍然是主体，市场相关分组在 VERIFIED 后才出现。

4. **管理设置保留在侧边栏**：单公司内部工具的管理员和主要用户往往是同一人或同一个小团队。把管理设置放在"系统"下保持可发现性，同时它永远在最末位，不影响主要工作流。后台 admin 面板仍然是数据连接等底层配置的权威入口。

5. **不消灭项目概念，而是自动解析**：后端继续使用 project 实体组织数据。前端通过系统设置中的"默认监控项目"自动选择广拓项目，用户无需手动选择。GEO 监测页面（问题库、运行报告等）仍然需要项目上下文——它们自动使用同一个默认项目。这不是"去掉项目"，而是"不让用户感知项目"。

### 首页模块（3 个，不超过首屏）

**模块 1 — 全链路概览**：4 个阶段卡片，每卡片展示核心指标和接入状态。状态分三种：
- **已接入**：显示真实数据
- **待接入**：来源系统有 API，本系统尚未对接（当前无此状态，预留）
- **来源不可用**：来源系统本身尚无 API（当前原始咨询和订单结果的状态）

**模块 2 — 投入与流量趋势**：两组独立趋势图，不合并到同一坐标轴。广告（消费/点击）和网站（访客/访问/PV）各用双 Y 轴折线，左右或上下并排。不画广告→网站的归因箭头或漏斗线。

**模块 3 — 需要关注**：异常列表，最多 3 条，每条必须可下钻。

### 全链路指标规则

| 阶段 | 主指标 | 辅助指标 | 当前状态 |
|---|---|---|---|
| 广告投放 | 广告消费 | 点击量、展现量 | 已接入（百度营销试点） |
| 网站访问 | 访客数(UV) | 访问次数、PV | 已接入（百度统计试点） |
| 原始咨询 | — | — | 来源不可用（落地页系统无 API） |
| 订单结果 | — | — | 来源不可用（销售系统无 API） |

环比/同比/转化率只有口径和数据窗口真实支持时才展示。V1 不计算广告→网站的转化率。

### 与上一版首页的差异

1. **去除指标冗余**：上一版全链路卡片显示了消费和点击，下方趋势图又展示消费和点击。本版趋势图只保留两个独立图表区域，不重复列出概览卡片已有的数字。
2. **区分"待接入"和"来源不可用"**：前者表示本系统排队接入，后者表示来源系统本身不具备 API。这对管理层的预期管理很重要。
3. **趋势图不合并广告和网站数据**：广告和网站使用独立图表，不暗示归因关系。
4. **异常条目有明确优先级规则**（见第八节）。

## 八、异常与行动

### 异常数量

首页最多展示 3 条。当候选异常超过 3 条时，按以下优先级选择：

1. **数据健康异常**优先于指标波动（数据源断了比数据差了更紧急）
2. **连续趋势**优先于单日波动（连续 3 天下降 > 单日突降）
3. **高影响指标**优先于低影响指标（消费异常 > 展现异常）
4. 同优先级时取**变化幅度最大**的

### V1 异常规则

| 异常类型 | 检测规则 | 下钻目标 |
|---|---|---|
| 数据更新延迟 | 上次成功刷新超过 30 分钟 | 管理设置 → 数据连接 |
| 消费异常波动 | 7 日滑动均值变化超过 ±20% 且连续 3 天同向 | 广告表现 / 对应日期 |
| 点击异常波动 | 7 日滑动均值变化超过 ±20% 且连续 3 天同向 | 广告表现 / 对应推广计划 |
| 访客异常波动 | 7 日滑动均值变化超过 ±15% 且连续 3 天同向 | 网站流量 / 对应日期 |
| 刷新失败 | 最近一次刷新状态为 FAILED 或 INTERRUPTED | 管理设置 → 数据连接 |
| 绑定异常 | 任一账户绑定暂停或连接需处理 | 管理设置 → 账户绑定 |

V1 只使用有明确计算口径的规则，不生成无法解释的 AI 建议。

消费和点击同时异常时合并为一条"搜索推广表现异常"，避免同一原因占多个坑位。

## 九、项目上下文的处理

### 问题

现有 GEO 功能（问题库、运行报告、项目看板、来源分析、SEO 检测）全部依赖 project 实体。前端当前通过 `/geo/projects` 让用户选择项目，然后各页面读取 URL 参数或 localStorage 中的 project_id。

### 方案

1. 后端新增系统设置项 `market.default_project_id`，管理员在管理设置中配置。
2. 前端所有页面从该设置项自动解析项目上下文，不要求用户手动选择。
3. `/geo/projects` 页面降级为管理设置中的"项目管理"子页面，仅管理员可见，用于创建和归档项目。
4. 当前已登录用户的最近使用项目偏好保留，作为默认项目未配置时的 fallback。

### 为什么不是"去掉项目"

项目实体是数据隔离和权限控制的基础。多品牌场景下同一套代码可以通过配置不同默认项目来服务不同品牌。消灭项目实体等于放弃未来的扩展性，而只需要隐藏项目选择器就能达到同样的 UX 效果。

## 十二、关键假设

1. 所有正式展示的百度账户和百度统计站点都属于广拓。
2. 内部用户默认查看同一套广拓市场数据。
3. 多个百度账户可以在统一口径下汇总。
4. 广告数据与网站流量当前只能同期对照，不能自动归因。
5. 咨询和销售系统未来能够提供稳定只读 API。
6. 后端 project 实体继续作为数据归属容器，前端通过默认项目设置自动解析。

## 十三、验收标准

1. 市场负责人进入首页 10 秒内能识别投入、流量和主要异常。
2. 管理层不需要理解 GEO、项目或数据接口即可读懂首页。
3. 首页核心业务模块不超过 3 个，首屏无需滚动即可看到全部核心数字和异常。
4. 未接入阶段不展示虚构数字、零值或模拟漏斗。
5. 广告与网站数据不会被错误描述为归因结果。
6. AI 搜索表现、引用来源分析、SEO 健康检测、问题库和运行报告均能从新侧边栏进入。
7. 桌面端首屏无横向滚动。
8. GEO/SEO 现有功能（问题库、运行报告、项目看板、来源分析、SEO 检测）的所有现有指标和交互完整保留。
9. 用户无需手动选择项目即可使用所有页面。
