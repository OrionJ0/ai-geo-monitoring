# 问题集运行与调度可靠性加固 PRD

## Problem Statement

问题集运行已经具备独立报告、失败重试、暂停恢复、CSV 往返和定时监测能力，但当前执行链仍存在会破坏最终业务目的的可靠性缺口：

- 同一定时执行在前一轮尚未结束时可能被下一次调度 tick 重复领取，造成重复平台调用、重复配额消耗和重复数据。
- 超时恢复只修改子任务，不保证父运行完成；旧执行器在租约被回收后仍可迟到写入，数据库已出现 `completed` 与“分析任务中断”错误并存的矛盾记录。
- SQLite 的 WAL、busy timeout 和 synchronous 设置实际未生效，多任务并发写入时遇锁即失败。
- 手动启动问题集时，运行实例、配额和任务记录不在同一事务；网络重试也没有初始运行幂等键，可能留下空运行、孤儿任务、配额泄漏或重复运行。
- 项目、问题和竞品清理会物理删除历史运行仍引用的任务记录。现有历史快照仍可查看，但部分旧报告已经无法重试。
- `analysis_only` 重试暂停后恢复时会丢失执行模式，退化为重新调用监测平台。
- CSV 可导入不可执行的 `pending` 行，形成永久“运行中”但不能暂停或恢复的只读报告。
- “部分完成”缺少失败原因和下一步操作；当前 PDF 列宽改动存在明细右侧被裁切的风险。

现有证据已经证明上述机制和数据污染。当前没有证据证明已经产生真实外部重复账单，也没有保存某个父运行永久空壳的完整事故时间线；因此本需求把“调度重复执行”和“租约失效后迟到写入/父运行不收敛”定义为生产发布阻断级 P0，而不把推断写成已发生的计费事故。

## Solution

建立一条可恢复、可幂等、可审计的问题集运行链路：

- 每个定时计划时槽只允许一个持久化执行实例，单进程和多进程并发都不能重复调用平台。
- 每个任务通过有过期时间的执行租约领取；所有终态写入必须携带相同租约令牌，过期执行器不能覆盖新状态。
- 任何任务队列排空、暂停排空或恢复完成后，系统统一收敛父运行并固化快照。
- 手动运行以幂等键为入口，在一个事务内完成运行实例、配额预留、全部任务和运行关联。
- 历史运行证据与当前项目缓存具有独立生命周期，项目编辑不能破坏已存在的历史报告和可重试性。
- 启动、恢复和数据库并发能力进入 readiness 与运行观测，不能只因 HTTP 存活就报告健康。
- 导入报告只能是不可执行的终态；报告明确展示失败数量、失败阶段、可执行操作和不可重试原因。

## Priority and Evidence Policy

- **P0 发布阻断**
  - 同一调度时槽可能被重复执行。
  - 执行租约没有 fencing，恢复后旧 worker 可迟到写入；恢复不保证父运行终态收敛。
- **P1 必须随本需求交付**
  - SQLite 并发配置失效。
  - 初始运行不原子且无幂等键。
  - 历史运行证据会被项目清理删除。
  - `analysis_only` 暂停恢复后退化。
  - imported pending 不可收敛。
  - CSV 数值边界缺失，可写入不可信 KPI。
  - partial 状态不可解释、不可操作。
  - PDF 明细宽度需要真实导出验收。
- **P2 延后或独立处理**
  - 问题集同名数据库唯一约束。
  - 空集/单题集前后端契约。
  - 问题跨问题集迁移语义。
  - 归档项目历史链接。
  - 分析口径版本标签、SOV 文案、导航与指标术语。

SQLite 配置失效本身没有已证实的数据损坏事故，不单独定义为 P0；但它是本需求 P0 并发修复上线前的强制门禁。

## User Stories

1. As a GEO 运营人员, I want 同一个定时监测时槽只执行一次, so that 我不会因调度重入承担重复平台成本或看到重复结果。
2. As a GEO 运营人员, I want 服务重启或任务超时后报告自动进入一致终态, so that 我不会面对永久转圈或状态互相矛盾的报告。
3. As a 项目负责人, I want 重复点击或网络重试复用同一次问题集运行, so that 配额和外部调用不会重复消耗。
4. As a 数据审计人员, I want 历史运行证据不受后续项目编辑影响, so that 报告长期可查看，并在数据完整时可重试。
5. As a 用户, I want “部分完成”报告告诉我哪些任务失败、为什么失败以及能否重试, so that 我能采取下一步行动。
6. As an 运维人员, I want 健康检查反映调度器、恢复器和数据库并发配置的真实状态, so that 服务不会在核心执行能力失效时仍显示健康。
7. As an 数据导入人员, I want 导入边界拒绝不可执行状态和非法数值, so that 只读历史不会伪装成正在执行的任务，也不会产生不可信指标。

## Scope

- In scope:
  - 定时执行的单进程 single-flight 和数据库级时槽去重。
  - 调度执行的持久状态、领取、恢复和可观测性。
  - 带过期时间的任务执行租约、续租和终态 fencing。
  - 恢复、暂停、重试和正常执行共用的父运行收敛规则。
  - SQLite WAL、busy timeout、synchronous 的可靠配置与启动验证。
  - 手动问题集运行的幂等键、原子创建和配额事务。
  - 运行计划中持久化计划平台、跳过平台及原因、竞品基线和分析契约版本。
  - 历史运行与任务记录的显式归属、存量回填和清理保护。
  - `analysis_only` 执行模式与重试批次在暂停恢复后保持不变。
  - imported CSV 禁止非终态行，并校验数字类型和业务范围。
  - 报告返回服务端计算的可执行能力与不可重试原因。
  - partial 报告的完成、失败、待处理数量、失败阶段和操作入口。
  - A4 PDF 明细右边界的真实导出验收。
  - 入口级、并发、故障注入、重启和真实浏览器验收证据。
- Out of scope:
  - 改变 soft pause 语义或取消已经在途的平台请求。
  - 改变现有品牌提及率、推荐率、排名、SOV 和引用指标口径。
  - 引入第二套问题集报告或保留旧执行路径作为 fallback。
  - 对已经丢失底层任务的旧报告伪造恢复数据。
  - 自动修复或改写旧报告的业务指标。
  - 问题集成员从单归属改为多对多。
  - 自动比较两次报告或生成 AI 解读。
  - 跨区域分布式“严格 exactly once”承诺；本需求保证同一持久化时槽只有一个有效执行所有者，并通过幂等与 fencing 阻止重复副作用。
- Later:
  - 问题集同名唯一约束及存量重名治理。
  - 空集、单题集和跨集迁移的统一产品契约。
  - 归档项目历史链接与分析口径版本筛选。
  - 定时计划的错过执行补跑策略、时区与 DST 完整治理。
  - 历史报告自动对比和趋势解释。

## Product Behavior

### 定时执行

- 同一个计划、同一个计划时槽只能创建一个执行实例。
- 单个 tick 尚未结束时，当前进程不会启动下一轮 tick。
- 多个进程同时发现同一到期计划时，只能有一个进程取得该时槽的执行权。
- 取得执行权后才允许扣配额、创建任务和调用平台。
- 进程在执行中退出时，执行实例保留为可诊断状态，并按统一恢复规则进入失败或继续执行，不会静默消失。
- 调度器未初始化、恢复失败或数据库并发配置未达到要求时，readiness 不得返回成功。

### 手动问题集运行

- 前端每次点击“运行问题集”生成一个稳定幂等键，并在超时重试时复用。
- 相同用户、项目、问题集和幂等键只能对应一个运行实例。
- 重复请求返回同一运行标识，并明确标记为幂等回放。
- 运行实例、任务槽位、全部任务记录和配额预留必须同时成功或同时失败。
- 事务失败时不显示历史运行、不消耗配额、不留下孤儿任务。
- 运行报告保留本次计划的平台列表，以及每个被跳过平台的安全原因。

### 任务执行与恢复

- 一个 pending 任务只有取得有效租约后才能调用监测平台或分析 API。
- 租约包含所有者、令牌和过期时间；长任务在有效执行期间续租。
- 成功、失败和指标持久化都必须验证租约令牌。
- 租约已被恢复器回收后，旧执行器的迟到结果不得改变任务或指标。
- 成功任务不保留旧错误信息；失败任务保留稳定失败阶段和安全错误码。
- 恢复器只处理已过期租约，不得因为另一个进程仍在执行就误杀活任务。
- 当一个运行已经没有 pending 任务时，系统必须写入 `completed_at`、终态快照和最终 revision。

### 暂停、继续与重试

- 继续保持 soft pause：停止领取新任务，已经取得租约的任务允许完成。
- 暂停后的在途任务全部结束时，如果没有 pending，报告自动收敛为终态。
- `analysis_only` 重试暂停后继续时复用已保存的原回答和供应商引用，不重新调用监测平台，也不消耗监测配额。
- 重试批次从 queued 到 running、completed 或 failed 必须可追踪，不得因暂停恢复永久停留在 queued。

### 历史证据

- 新运行的任务必须具备明确的运行归属和稳定槽位。
- 编辑问题、竞品或项目配置不得删除问题集运行仍引用的证据。
- 对存量报告执行一次性完整性盘点：
  - 底层任务仍完整：保持可重试。
  - 底层任务缺失但快照存在：保持只读可查看，明确显示不可重试原因。
  - 活跃运行数据不完整：进入可诊断失败状态，不得继续显示无期限运行中。
- 删除整个项目时继续遵循现有项目删除授权与级联语义；不得把“历史证据保护”扩大为绕过用户明确删除项目。

### CSV 与报告交互

- imported CSV 只接受 `completed` 和 `failed` 等终态，不接受 `pending`。
- ID 必须为正整数；次数不得为负数；排名和百分比必须处于业务允许范围。
- 导入失败返回具体行号、字段名和稳定错误码，不创建半份报告。
- imported 报告不显示暂停、继续或执行型重试。
- 报告接口直接返回 `can_pause`、`can_resume`、`can_retry` 和不可执行原因，前端不再仅靠 source/status 猜测。
- partial 报告展示“完成 / 失败 / 待处理”数量、失败阶段摘要和可用操作。
- PDF 导出必须完整包含明细表最右侧列，不允许依赖浏览器横向滚动区域被自动裁切。

## Acceptance Criteria

### P0 发布门禁

- AC-001: Given 同一个定时计划时槽被两个 tick 或两个进程同时发现, When 两者尝试领取, Then 只创建一个有效执行实例，只扣一次配额，只产生一组任务。
- AC-002: Given 一次调度执行持续超过 30 秒, When 后续 interval tick 到达, Then 同一计划时槽不会再次调用监测平台。
- AC-003: Given worker 的租约已经过期并被恢复器处理, When 旧 worker 迟到提交成功或失败结果, Then 数据库拒绝该写入且不会改变任务、指标和父运行 revision。
- AC-004: Given 活跃 worker 持有尚未过期且持续续租的租约, When startup 或周期 recovery 执行, Then 该任务不会被误判为中断。
- AC-005: Given recovery、暂停排空或正常队列排空后运行已无 pending, When 收敛逻辑执行, Then `completed_at` 非空、终态快照完整、父状态与子任务一致。
- AC-006: Given scheduler 初始化或首次 recovery 失败, When 服务开始接受流量, Then readiness 返回失败且系统会记录可操作错误，不得只返回 HTTP 健康。

### 数据库与启动

- AC-007: Given 本地 SQLite 启动完成, When 读取 PRAGMA, Then `journal_mode=wal`、`busy_timeout>=5000`、`synchronous=normal`，否则 readiness 失败。
- AC-008: Given 使用 Postgres, When 服务启动, Then 不执行 SQLite PRAGMA，调度、租约和唯一约束仍具有等价行为。

### 初始运行与配额

- AC-009: Given 相同项目、问题集和幂等键被并发提交多次, When 请求处理完成, Then 返回同一个 run ID，只有一次配额预留和一批任务。
- AC-010: Given 创建第 N 条任务或写入运行关联时发生异常, When 事务回滚, Then 不存在空 run、部分任务、孤儿任务或配额变化。
- AC-011: Given 运行计划包含不可用平台, When 报告进入终态, Then 报告、CSV 和 PDF 仍可看到计划平台、跳过平台及原因。

### 租约、状态与重试

- AC-012: Given 一个任务成功完成, When 查看任务和 CSV, Then `status=completed` 时不得残留旧 `error_message`。
- AC-013: Given `analysis_only` 重试被暂停后继续, When 执行完成, Then 不调用监测平台、不消耗监测配额，并复用原回答和引用快照。
- AC-014: Given retry batch 被暂停后继续, When 所有任务结束, Then batch 进入 completed 或 failed，不停留在 queued。
- AC-015: Given partial 报告, When 用户打开报告, Then 可以看到完成数、失败数、待处理数、失败阶段摘要以及可用的重试或不可重试原因。

### 历史证据

- AC-016: Given 新运行已创建, When 后续编辑或删除该问题的当前分析数据, Then 运行证据仍可查看，完整记录仍可重试。
- AC-017: Given 旧报告底层记录已缺失但快照存在, When 用户打开报告, Then 报告保持可读并显示 `can_retry=false` 与明确原因，不再提供必然返回 409 的按钮。
- AC-018: Given 活跃运行关联记录被发现缺失, When 完整性检查执行, Then 运行进入可诊断失败状态，不得无限显示 running。

### 导入与导出

- AC-019: Given CSV 包含 pending 行, When 用户导入, Then 返回 422、指出行号和状态问题，且数据库不新增报告。
- AC-020: Given CSV 包含负 ID、小数 ID、负计数、非法排名或超范围百分比, When 用户导入, Then 返回字段级 422 且不产生部分写入。
- AC-021: Given imported 报告, When 用户打开详情, Then 页面不显示暂停、继续和执行型重试。
- AC-022: Given 当前排版报告包含全部列, When 导出 A4 竖版 PDF, Then 每页右边界和最后一列完整可见。

### 正式切换与证据

- AC-023: 正式 `POST /question-sets/:id/run` 只调用新的原子启动入口；旧的“先建空 run、后回写 record_ids”路径被删除且没有隐藏 fallback。
- AC-024: 入口级测试证明新实现被调用、旧实现未被调用。
- AC-025: 交付证据至少包括并发领取、故障注入、真实重启、SQLite PRAGMA、API 幂等回放、数据库不变量和真实 PDF 截图。

## Metrics / Success

- 同一计划时槽的有效执行实例重复率为 0。
- 相同初始运行幂等键产生的 run 数、配额预留数和任务批次数均为 1。
- 新产生的 completed 任务中，残留错误信息数量为 0。
- 无 pending 的 native run 中，`completed_at IS NULL` 数量为 0。
- 新问题集运行的任务归属完整率为 100%。
- imported 报告处于 running/paused 的数量为 0。
- scheduler readiness、最近 tick、最近 recovery 和租约拒绝迟到写入均可观测。
- A4 PDF 明细最右列像素验收通过率为 100%。

## Constraints

- 同时支持本地 SQLite 和生产 Postgres。
- 现有报告链接、历史快照和合法 CSV v1 文件必须继续可读。
- API 变更优先增加字段；需要强制幂等键时，前后端必须在同一发布切片完成正式切换。
- soft pause 语义保持不变，不承诺取消已在途请求或返还其配额。
- 不重新启用旧指标启发式规则，不增加旧运行路径 fallback。
- 旧报告缺失底层记录时保留事实，不伪造可重试性。
- 第三方平台响应、CSV 和客户端幂等键仍按不可信输入处理。
- 数据迁移必须先备份并提供只读审计结果，不得静默删除快照。
