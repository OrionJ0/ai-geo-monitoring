# 市场部虚拟机共享运行与 DeepSeek Web 排队状态 PRD

状态：阻塞（实现与自动化验收完成，待目标虚拟机真实入口验收）

日期：2026-07-27

关联需求：`docs/closed-2026-07-26-002-deepseek-web-monitoring/prd.md`

## 需求总结

`ai-geo-monitoring` 主要供公司市场部内部使用。市场部同事不会在个人电脑上安装或运行项目，而是通过浏览器访问部署在公司虚拟机上的统一服务。

市场部有多位同事，可能同时登录系统、查看同一批品牌项目，并同时运行单个问题或问题集。DeepSeek Web 监测仍使用一个公司统一管理的 DeepSeek 账号，所有真实页面采集都发生在虚拟机上的专用 Chrome 中，而不是访问者自己的电脑中。

本期需要解决的是多人同时操作时的排队、状态理解和运维边界，而不是建设完整的企业级多租户系统。方案必须保持内部工具所需的低复杂度：

- 市场部多人可以同时从各自浏览器访问和提交运行。
- 所有市场部同事统一使用现有 `admin` 系统账号访问共同的项目和报告。
- DeepSeek Web 使用一个服务账号、一个持久 Chrome profile 和一个活动页面。
- DeepSeek Web 任务全局串行；DeepSeek API 和其他 API 平台继续按原有方式并发。
- 用户能理解任务是在排队、运行、等待人工登录，还是已经失败。
- 登录状态保存在虚拟机的专用 Chrome profile 中，应用不保存 DeepSeek 账号密码。
- 不引入 Redis、BullMQ、多浏览器、账号池、代理池或完整团队权限系统。

## 当前问题

1. **部署位置容易误解**

   市场部同事从个人电脑访问系统，但 DeepSeek Chrome 实际运行在后端所在虚拟机。若虚拟机没有持续可用的桌面会话、Chrome 或持久磁盘，Web 采集无法正常工作。

2. **多人可以同时提交，但 Web 页面不能同时操作**

   多个浏览器请求可以并发到达后端，同一个 DeepSeek 账号和页面却不应并发发送问题，否则可能产生上下文污染、会话竞争、页面状态错配或风控。

3. **排队状态不够直观**

   当 Web 队列前方已有任务时，用户可能把等待误认为按钮无效、浏览器卡死或运行失败，并重复提交相同问题。

4. **共享账号与个人账号的边界不清楚**

   如果立即为每位同事建立独立系统账号，还要让他们共享品牌项目和报告，就需要新增团队、项目成员、角色权限、邀请、移除和审计等完整协作模型，明显超出内部工具当前需要。

5. **登录失效需要统一恢复方式**

   DeepSeek 登录过期、出现验证码或需要切换账号时，市场部使用者无法在自己的电脑上处理虚拟机中的 Chrome，需要由虚拟机运维负责人进入虚拟机人工恢复。

6. **单进程约束必须成为正式运行约束**

   当前 DeepSeek Web FIFO 和浏览器会话由单个后端进程管理。若误启动多个后端实例，会破坏全局串行假设，并竞争同一个 Chrome profile。

7. **失败不能被伪装成其他结果**

   浏览器无响应、登录失效、验证码、页面结构变化或等待回答超时都必须保留为明确失败，不得静默改用 DeepSeek API，也不得生成替代答案。

## Problem Statement

市场部需要把系统当作一个统一的内部 Web 工具使用，而不是每位同事各自维护一套本地运行环境。多人可能同时发起监测，但 DeepSeek Web 第一版只能安全地使用一个虚拟机浏览器和一个 DeepSeek 服务账号串行采集。

如果系统只在技术上排队、却没有明确展示 Web 通道状态，用户会把正常等待理解为故障并重复提交。如果为了多人访问直接引入多账号、多浏览器、分布式队列或完整项目协作权限，又会让当前内部工具承担不必要的建设和维护成本。

因此，需要在不改变现有 GEO 主链路的前提下，正式定义“一台虚拟机、一个后端、一个 DeepSeek 账号、多人提交、单浏览器串行消费”的产品行为和运维边界。

## Solution

采用“多生产者、单消费者”的内部部署模型：

```text
市场部多人浏览器
   ├── 同事 A
   ├── 同事 B
   └── 同事 C
          ↓ 同时提交
现有后端 + 持久任务记录
          ↓
DeepSeek Web 全局 FIFO
          ↓
虚拟机上的一个专用 Chrome
          ↓
一个 DeepSeek 服务账号
```

### 1. 访问与账号

- 所有市场部同事统一使用现有 `admin` 系统账号登录 `ai-geo-monitoring`，共同查看和操作品牌项目、问题库、运行报告和分析结果。
- 共享 `admin` 账号保留现有完整管理员权限；第一版不增加市场部专用角色、权限裁剪或个人操作审计。
- DeepSeek Web 使用一个由虚拟机运维负责人维护的公司服务账号。
- 系统 `admin` 账号和 DeepSeek 服务账号是两套不同身份，不得混为一套凭据。
- 系统不读取、保存或展示 DeepSeek 密码、Authorization 或 Cookie；登录会话由虚拟机专用 Chrome profile 自行保存。

### 2. 并发与队列

- 多位市场部同事可以同时提交单问题或问题集运行。
- 每次提交继续创建独立的运行报告和持久任务记录。
- 所有 `deepseek-web` 问题进入同一个先进先出队列，同一时刻最多一个问题处于页面交互或采集阶段。
- DeepSeek API 和其他 API 平台不进入 Web 队列，继续使用原有并发能力。
- 一次 HTTP 请求的重复传输继续由幂等键防重；来自不同浏览器的两次明确提交视为两次独立运行，不在服务端静默合并。
- 暂停采用协作式语义：暂停前已经取得执行权的任务允许完成，尚未领取的任务保持暂停，恢复后再继续调度。

### 3. Web 通道状态

系统向已登录用户提供统一、只读的 DeepSeek Web 运行状态，至少区分：

- `idle`：浏览器通道可用且当前没有 Web 任务。
- `busy`：当前至少有一个可执行 Web 问题正在等待或运行。
- `login_required`：需要虚拟机运维负责人重新人工登录。
- `verification_required`：需要虚拟机运维负责人完成人工验证。
- `unavailable`：Chrome、桌面会话、profile、页面结构或浏览器连接当前不可用。
- `shutting_down`：后端正在关闭，不再接受新的 Web 页面工作。

状态中展示的是“当前仍可执行或已经取得执行权”的 Web 问题数量。已暂停且没有有效执行租约的休眠记录不计入全局等待数；暂停前已经取得有效执行租约的记录在完成或租约过期前仍计入。第一版不承诺精确队列位置或预计完成时间，避免用户依赖不稳定的时间估算。

### 4. 运行状态展示

- 用户提交成功后立即进入该次独立运行报告。
- 报告明确显示“排队中”“运行中”“已完成”“部分失败”或“失败”。
- 当 Web 通道繁忙时，界面说明任务已经进入队列，不提示用户重复提交。
- 问题集中的 DeepSeek Web 问题逐条进入同一队列；其他 API 平台结果可以先完成并在同一报告中持续更新。
- 暂停问题集后，报告继续显示“已暂停”；暂停前已经开始调度的少量任务可能完成，未领取记录不再污染全局 Web 等待数量。
- 运行报告和历史记录继续明确区分 `deepseek` 与 `deepseek-web`，不合并样本。

### 5. 浏览器生命周期

- 第一条 Web 任务到达时，由后端在虚拟机上启动专用 Chrome。
- 成功任务结束后保留浏览器进程和 profile，并释放 Web 执行权处理下一条任务；不为每个问题重复启动和关闭 Chrome。
- 每个问题仍创建新对话，避免不同市场同事或不同运行之间发生上下文污染。
- 浏览器连接关闭、命令失败、无响应或生成超时时，当前任务明确失败，异常浏览器会话被关闭回收，下一条任务重新启动 Chrome。
- 后端正常关闭时关闭专用 Chrome 并释放 profile 锁。

### 6. 登录、验证与账号切换

- 首次登录、登录失效、验证码和 DeepSeek 账号切换均由虚拟机运维负责人通过虚拟机桌面或远程桌面人工处理。
- 运维负责人停止占用专用 profile 的后端进程后，执行：

  ```bash
  npm run web:login -- deepseek-web
  ```

- 在打开的虚拟机 Chrome 中完成登录或切换账号，确认对话输入区域可用后关闭登录命令启动的浏览器，再恢复后端。
- 登录、验证或选择器错误形成的进程内熔断只在后端重启后清除，因此完成登录或账号切换后必须重新启动后端，不能只关闭登录浏览器。
- 已经遇到登录或验证失败的运行保留失败记录和重试入口；恢复登录后由用户从原运行报告重试。
- Web 登录失败时不得回退 DeepSeek API。

### 7. 虚拟机运行约束

- 正式环境只运行一个后端实例。
- 虚拟机必须安装受支持的 Chrome，并保持可用的图形桌面会话。
- 虚拟机不得休眠；远程访问断开后桌面会话仍应持续存在。
- DeepSeek Web profile、证据目录和数据库必须位于持久磁盘。
- profile 不得与运维人员日常 Chrome、SEO 临时浏览器或其他应用共用。
- 市场部使用者只访问 `ai-geo-monitoring` Web 页面，不需要也不应该直接访问虚拟机 Chrome。

## User Stories

1. As a 市场部同事, I want to 直接通过浏览器访问统一部署的系统, so that 我不需要在个人电脑安装或维护项目。
2. As a 市场部同事, I want to 在其他同事正在运行 DeepSeek Web 时继续提交问题, so that 我的任务可以排队而不是被直接拒绝。
3. As a 市场部同事, I want to 看见 Web 通道是空闲、运行中还是等待管理员处理, so that 我不会把正常排队误认为系统故障。
4. As a 市场部同事, I want to 每次提交都进入独立运行报告, so that 多人同时操作时结果仍然可以按运行核对和重试。
5. As a 市场部同事, I want to DeepSeek API 和 DeepSeek Web 继续显示为两个独立平台, so that 真实网页样本不会与 API 样本混淆。
6. As a 市场部负责人, I want to 所有人统一使用现有 admin 系统账号和同一批品牌项目, so that 不需要先建设完整团队权限系统。
7. As a 虚拟机运维负责人, I want to 在虚拟机中统一维护 DeepSeek 登录和验证, so that 市场部同事不需要接触 DeepSeek 凭据或虚拟机桌面。
8. As a 虚拟机运维负责人, I want to 浏览器异常后自动回收并由后续任务重新启动, so that 一个坏会话不会永久阻塞整个队列。
9. As a 虚拟机运维负责人, I want to 后端保持单实例运行, so that 所有 Web 任务始终遵守同一个 FIFO 和 profile 锁。
10. As a 数据使用者, I want to Web 失败时保留明确错误和页面采集阶段, so that 报表中不会出现伪造或来源不明的成功结果。

## Scope

- In scope:
  - 一台虚拟机、一个后端实例的内部部署模型。
  - 多个市场部浏览器同时访问和提交运行。
  - 所有市场部同事统一使用一个现有 `admin` 系统账号。
  - 一个 DeepSeek 服务账号、一个持久 Chrome profile 和一个活动页面。
  - DeepSeek Web 全局 FIFO 串行采集。
  - DeepSeek Web 通道状态和等待任务数量的用户可见提示。
  - 单问题和问题集的排队、运行、失败、报告与重试说明。
  - 虚拟机运维负责人执行人工登录、验证和账号切换流程。
  - 成功复用浏览器、异常回收浏览器和后端关闭浏览器。
  - API/Web 样本隔离和 Web 失败不回退 API。
  - 虚拟机桌面会话、持久目录和单实例运行约束。

- Out of scope:
  - 为每位市场部同事建立可共享项目的个人工作区。
  - 团队、项目成员、邀请、角色权限、审批或个人操作审计。
  - 企业 SSO、LDAP、OAuth 或即时通讯登录。
  - 多个 DeepSeek 账号、账号轮换或账号池。
  - 多浏览器、多标签页并行采集。
  - 多后端实例、独立 Web Worker 或跨机器队列。
  - Redis、BullMQ、ClickHouse 或新的任务系统。
  - 自动输入密码、自动处理验证码或规避平台风控。
  - 代理池、Camoufox、反指纹或无人值守账号恢复。
  - 精确队列位置和预计完成时间承诺。
  - 市场部用户直接控制或查看虚拟机中的 DeepSeek Chrome。

- Later:
  - 当确实需要人员级权限和审计时，增加个人系统账号与共享工作区，但仍保持 DeepSeek 服务账号独立。
  - 当 Web 队列长期积压且等待时间不可接受时，评估多个独立 DeepSeek 服务账号和对应的独立 profile；每个账号内部仍串行。
  - 只有需要多个后端实例或跨机器协调时，才评估外部队列。

## Product Behavior

### 1. 市场部访问

- 市场部同事从个人电脑浏览器访问虚拟机对外提供的系统地址。
- 页面和 API 请求仍由虚拟机上的前后端处理。
- 个人电脑不启动 Chrome 自动化进程，也不保存 DeepSeek 登录状态。

### 2. 同时提交

- 两位或更多同事同时运行不同问题时，每次提交都获得独立 `run_id` 和报告地址。
- DeepSeek Web 任务按后端接收并成功持久化的顺序进入全局队列。
- API 平台可以先于 Web 平台返回结果，报告按各任务实际状态更新。
- 不允许因为 Web 通道忙而把问题改发 DeepSeek API。

### 3. 重复提交

- 同一次前端操作因网络重试重复发送时，幂等键返回原运行，不重复扣减配额或创建记录。
- 两个浏览器分别主动点击运行，即使问题相同，也创建两次独立样本。
- 页面在任务已经提交后明确显示报告和排队状态，降低误操作造成的重复样本。

### 4. 排队与空状态

- 没有 Web 任务时显示“DeepSeek Web 当前空闲”。
- 有任务等待或运行时显示“DeepSeek Web 正在处理，其他 Web 问题将按顺序执行”及当前等待数量。
- 全局等待数只统计仍可被调度或已取得有效执行租约的任务，不统计已暂停运行中尚未领取的休眠记录。
- 第一版不显示分钟级 ETA，也不承诺某个任务固定排在第几位。
- 用户离开页面或关闭个人浏览器，不影响虚拟机上的任务继续执行。

### 5. 暂停与恢复

- 暂停是协作式停止继续领取，不是强制取消已经开始调度的请求。
- 暂停信号到达前已取得有效执行租约的任务允许完成；当前配置可能有不止一条这类任务，但真实 Web 页面采集并发仍始终为 1。
- 尚未取得执行租约的 pending 记录在暂停期间保持休眠，不计入全局 Web 等待数量；恢复后重新进入可执行等待数。
- 前端提示使用“已开始调度的任务完成后暂停”，不得承诺只有单个“当前任务”会继续。

### 6. 登录与验证异常

- 通道需要登录或验证时，市场部页面显示“需要虚拟机运维负责人处理”，不要求市场部用户输入 DeepSeek 凭据。
- 新运行在规划阶段发现通道不可用时，不为该平台创建假成功记录，也不消费其监测配额。
- 已经开始后才发现登录或验证异常的任务进入失败状态，并保留可重试报告。
- 运维负责人恢复后，用户从原报告重新提交失败项。

### 7. 浏览器异常

- 浏览器无响应、命令失败、连接关闭或生成超时必须显示不同的稳定失败代码和用户可读说明。
- 异常会话被回收后，后续任务可以启动一个新 Chrome。
- 自动重启浏览器不等于自动重新发送已经提交过的问题；是否重试由用户在报告中确认。

### 8. 共享 admin 账号限制

- 所有市场部同事看到同一个 `admin` 账号名下的项目、问题和报告。
- 所有市场部操作在应用记录中都归属于同一个 `admin` 身份，无法据此识别真实操作人。
- 共享账号拥有现有完整管理员权限，包括设置、用户和高风险管理操作；第一版接受该边界，不增加权限裁剪。
- 第一版不提供“由哪位真实同事操作”的可靠审计。
- `admin` 账号的发放、密码轮换和离职人员撤权由公司内部账号管理流程负责。
- DeepSeek 服务账号凭据只由虚拟机运维负责人维护，不向市场部用户分发。

## Acceptance Criteria

- AC-001: 市场部用户无需安装项目，只通过个人电脑浏览器即可访问虚拟机上的系统。
- AC-002: DeepSeek Web Chrome 只运行在后端所在虚拟机，个人访问设备不启动采集浏览器。
- AC-003: 正式环境只启动一个后端实例，并能检测或阻止同一 DeepSeek profile 被第二个进程同时占用。
- AC-004: 至少两位用户可以同时提交不同的单问题运行，两次请求都返回独立运行报告。
- AC-005: 同时提交的 DeepSeek Web 问题最大页面采集并发数始终为 1。
- AC-006: DeepSeek API 和其他 API 平台不进入 Web FIFO，可以与 Web 任务并行执行。
- AC-007: 用户提交 Web 任务后能在报告中区分排队中、运行中、完成和失败。
- AC-008: 用户可以看到 DeepSeek Web 通道的空闲、忙碌、需要登录、需要验证、不可用和关闭中状态。
- AC-009: 忙碌状态展示当前等待的 Web 问题数量，但不展示无法保证的精确 ETA。
- AC-010: 同一幂等键的重复请求只创建一次运行、配额预留和任务记录。
- AC-011: 不同浏览器的两次主动提交各自生成独立运行，不被静默合并。
- AC-012: 每个 Web 问题使用新对话，连续处理不同用户提交的问题时不存在上下文串扰。
- AC-013: 成功任务结束后浏览器保持可复用，下一条任务无需重新人工登录。
- AC-014: 浏览器连接、命令、无响应或生成超时后，异常会话被回收，后续任务可以重新启动 Chrome。
- AC-015: 后端正常关闭后，专用 Chrome 被关闭且 profile 锁被释放。
- AC-016: 登录过期或需要验证时，市场部用户看到需要虚拟机运维负责人处理的提示，不看到或输入 DeepSeek 密码。
- AC-017: 虚拟机运维负责人可以通过虚拟机桌面和 `npm run web:login -- deepseek-web` 恢复或切换 DeepSeek 账号。
- AC-018: 登录恢复后，原失败运行仍保留，并可以从对应运行报告重试失败项。
- AC-019: 任意 Web 失败都不会调用 DeepSeek API、生成替代回答或写入假成功结果。
- AC-020: `deepseek` 与 `deepseek-web` 在任务、历史、报告、筛选、聚合和导出中始终保持独立。
- AC-021: 应用代码、配置、数据库、日志和证据文件不保存 DeepSeek 明文密码或 Authorization。
- AC-022: 用户关闭个人浏览器或离开报告页后，虚拟机中的已提交任务仍继续执行。
- AC-023: 虚拟机重启或后端异常退出后，持久任务记录可以恢复，已完成报告不会丢失。
- AC-024: 第一版统一使用现有 `admin` 账号，不要求个人用户、共享工作区、Redis、BullMQ、多浏览器或多 DeepSeek 账号。
- AC-025: 仅存在已暂停且没有有效执行租约的 Web 记录时，公共 Web 通道状态不显示繁忙，这些记录在恢复运行后重新计入等待数。
- AC-026: 暂停前已经取得有效执行租约的 Web 记录在完成或租约过期前仍计入公共待处理数，真实页面采集最大并发仍为 1。
- AC-027: 暂停提示明确为“已开始调度的任务完成后暂停”，不承诺只有一个当前任务会继续完成。
- AC-028: 至少两个浏览器持续查看运行报告和 Web 通道状态时，不因正常轮询收到 `429`。
- AC-029: 完成人工登录、验证或账号切换后，运维流程必须重启后端以清除进程内熔断，再从真实运行入口验证恢复。

## Metrics / Success

- DeepSeek Web 页面采集观测到的最大并发数为 1。
- 两个及以上浏览器同时提交时，已接受运行丢失数为 0。
- 同一幂等请求重复创建运行或重复扣减配额的次数为 0。
- DeepSeek Web 失败后回退 API 或生成替代回答的次数为 0。
- API 平台因 Web 队列等待而被串行阻塞的次数为 0。
- 用户可见 Web 通道状态与后端实际状态不一致的持续时间不超过一个前端轮询周期。
- 正常的双浏览器报告与状态轮询触发 `429` 的次数为 0。
- 浏览器异常被回收后，后续任务能够重新启动会话，无需重启整套应用。
- DeepSeek 明文密码、Authorization 或 Cookie 进入应用配置、数据库、日志或证据文件的事件数为 0。
- 市场部使用期间因“不知道任务正在排队”而重复报障的数量可被持续记录并下降。

## Constraints

- 本系统是内部低并发工具，优先保证可理解、可恢复和样本可信，不追求 Web 高吞吐。
- 第一版部署必须保持单虚拟机、单后端进程、单 DeepSeek 账号、单 profile 和单活动页面。
- 虚拟机必须具有可持续运行的图形桌面会话，且不能进入休眠。
- 共享 `admin` 账号保留完整管理员权限且不提供个人级操作审计；接受这一限制是保持首期低复杂度的前提。
- DeepSeek 页面、登录和验证码属于外部不稳定依赖，系统必须默认失败关闭。
- Web 队列等待时间取决于前方问题数量和页面生成时间，第一版不承诺固定完成时限。
- 状态轮询必须有独立的只读限流预算；运行中报告降低轮询频率，暂停报告进一步降频，历史抽屉不得跟随每次报告轮询重复刷新。
- 只有在实际容量、权限或审计证据证明当前边界不足后，才能扩展多账号、工作区或分布式队列。
