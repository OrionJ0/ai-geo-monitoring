## Problem Statement

当前系统已经支持豆包 API 平台 `doubao`，也已通过 `deepseek-web` 建立真实网页监测能力。但豆包 API 返回不能代表市场部同事在豆包官方网页中实际看到的回答、联网搜索过程、引用和页面呈现。

市场部需要在现有项目、问题库、问题集和自动监测流程中采集豆包官方网页样本，并与豆包 API、DeepSeek Web 样本进行独立比较。该能力必须解决以下问题：

- 每次豆包 Web 提问都使用普通模式；联网由豆包普通对话自身提供，系统不点击或启用“深入研究”。
- 每个问题必须使用新会话，避免不同问题、项目或同事之间发生上下文串扰。
- 回答正文、引用、截图和运行信息必须可复核，不能把页面中无关的普通链接或检索候选误计为引用。
- `doubao-web` 与 `doubao` 必须是两个独立平台，网页失败时不得静默回退到 API。
- 豆包 Web 与 DeepSeek Web 必须使用不同的服务账号、浏览器会话和证据空间，不能相互阻塞或污染。
- 市场部多人通过目标虚拟机上的共享系统使用该能力时，需要理解豆包 Web 当前是空闲、排队、运行，还是需要运维人员处理。

本需求的目标不是建设任意网站自动化框架，而是在现有 GEO 监测主链路中新增一个可信、隔离、可运维的豆包 Web 正式平台。

## Solution

将豆包官方网页版注册为内置托管平台 `doubao-web`，显示名称为“豆包网页版”，并与豆包 API 平台 `doubao` 完全分离。

系统在目标虚拟机上使用豆包专用 Chrome Profile 和公司豆包服务账号。账号登录、验证码和人工验证由虚拟机运维负责人在真实浏览器中完成；系统不接收或保存豆包账号密码。

管理员可以在 `/admin/settings` 查看两个受管 Web 平台是否具备浏览器、是否已初始化专用 Profile、当前进程是否验证过登录，并从设置页打开对应专用 Chrome 完成人工登录或账号切换。页面只展示有界状态，不读取或展示账号身份、凭据和 Profile 路径。

每次执行豆包 Web 问题时，系统创建新会话，确认“深入研究”未启用并保持普通模式，提交问题，等待当前回答完整结束，再保存页面可见正文、平台展示的引用、截图和有界运行信息。无法确认普通模式时任务直接失败且不发送问题；网页采集失败时不调用豆包 API 生成替代结果。

豆包 Web 与 DeepSeek Web 共用一致的产品能力和运行语义，但保持独立的账号、Profile、浏览器实例、FIFO 队列、故障状态和证据目录。两个 Web 平台可以在同一台目标虚拟机上并行工作，每个平台内部仍保持单页面串行。

豆包 Web 与 DeepSeek Web 作为默认停用的内置预置平台交付，必须由管理员主动启用。新项目默认只包含两个已启用且可选择的 Web 平台；API 平台不默认加入，但用户可以按项目添加并与 Web 平台共同运行。如果任一所选 Web 平台未登录、会话失效、需要人工验证或浏览器不可用，运行应在任务创建前整体阻断并引导管理员处理，绝不跳过该 Web 平台或回退 API。已有数据库的管理员启停选择不会被预置同步覆盖。

## User Stories

1. As a 市场部同事, I want to 在问题库中选择豆包网页版运行问题, so that 我可以获得豆包官方网页的真实回答样本。
2. As a 市场部同事, I want to 分别查看豆包 API 与豆包 Web 记录, so that 两种来源不会在历史、报告和指标中混淆。
3. As a 市场部同事, I want to 每次提问都使用一个新会话, so that 之前的问题不会影响当前回答。
4. As a 市场部同事, I want to 豆包 Web 始终使用自带联网搜索的普通模式, so that 结果贴近用户默认使用体验且不会因“深入研究”增加时延和验证风险。
5. As a 市场部同事, I want to 查看回答、引用和截图证据, so that 我可以复核报告所依据的真实页面结果。
6. As a 市场部同事, I want to 在豆包 Web 忙碌时继续提交任务并看到排队状态, so that 我不会把正常等待误认为故障。
7. As a 市场部同事, I want to 豆包 Web 继续支持单问题、问题集、失败重试和自动监测, so that 我不需要使用另一套操作流程。
8. As a 虚拟机运维负责人, I want to 从设置页打开专用 Chrome、人工登录并验证后复用豆包专用会话, so that 日常任务不需要反复输入账号或处理验证。
9. As a 虚拟机运维负责人, I want to 豆包 Web 与 DeepSeek Web 的浏览器和故障状态相互隔离, so that 一个平台异常不会直接阻塞另一个平台。
10. As a 数据使用者, I want to Web 失败时保留明确错误且绝不回退豆包 API, so that 报告中的样本来源始终可信。
11. As a 系统管理员, I want to 在设置页区分浏览器配置、Profile 初始化、未登录、人工验证和页面结构异常, so that 我能判断网页版是否真的可用并安全切换账号。

## Product Behavior

### 1. 平台身份与样本隔离

- `doubao` 始终表示豆包 API 样本。
- `doubao-web` 始终表示豆包官方网页样本。
- 项目平台选择、问题平台选择、历史记录、运行报告、筛选、聚合和导出必须分别展示两个平台。
- 系统不得把 `doubao-web` 归一化为 `doubao`，也不得将两者合并为同一平台数据。
- 豆包 Web 的模型字段使用稳定界面标识 `doubao-web-ui`，不推测页面背后的实际模型版本。
- 豆包 Web 仅用于真实页面监测，不作为结构化分析平台、问题建议平台、模型目录来源或 API 连接测试平台。

### 2. 登录与专用运行环境

- 虚拟机运维负责人优先在 `/admin/settings` 选择 `doubao-web`，查看当前配置状态并启动豆包专用 Chrome；统一 Web 登录命令作为后端或设置页不可用时的运维备用入口。
- 运维负责人在真实豆包页面中人工完成登录、验证码、账号选择和必要验证。
- 账号切换会回收并重开该平台的专用 Chrome；在管理员完成主动验证前，该平台拒绝新的页面采集，另一个 Web 平台不受影响。
- 系统检测到可用对话输入区后，才能将登录状态视为可用。
- 登录状态由豆包专用 Chrome Profile 保存，服务重启后继续复用。
- 豆包 Profile 不得与 DeepSeek Web、日常 Chrome、SEO 浏览器或其他应用共用。
- 系统不要求用户复制 Token，不读取、保存或展示账号密码、Authorization 和 Cookie。
- 设置页只展示浏览器是否配置、Profile 是否初始化、当前登录验证结果、原因码和最近验证时间，不展示账号身份或服务器路径。
- 登录失效、需要验证或账号切换时，用户看到设置中心入口和“在运行后端的机器上打开专用 Chrome”说明。

### 3. 运行前检查

开始豆包 Web 任务前，系统至少检查：

- 豆包 Web 是否已经由管理员启用。
- 受支持的 Chrome 是否可用。
- 豆包专用 Profile 是否可读写且未被其他进程占用。
- 豆包官方页面是否可访问。
- 当前服务账号是否已登录。
- 新建会话、输入区和普通模式是否可以识别。
- 当前页面是否仍符合受支持的采集规则版本。

如果在任务创建前已经确认豆包 Web 不可用：

- 页面说明具体不可用原因。
- 整次运行不创建任何任务或伪成功记录。
- 整次运行不消费监测配额。
- 不跳过豆包 Web 后继续执行其他 Web 或 API 平台。

如果任务开始后才发现登录、验证、页面结构或浏览器异常，则当前记录进入失败状态并保留对应错误。

### 4. 单次采集流程

每个豆包 Web 问题按以下行为执行：

1. 等待获得豆包 Web FIFO 执行权。
2. 打开或恢复豆包专用浏览器会话。
3. 创建新会话，并确认没有复用前一个问题的上下文。
4. 确认“深入研究”没有启用；若存在单一明确的残留选中态，只关闭一次。
5. 从页面状态确认当前为普通模式。
6. 只有普通模式确认成功后，才输入并发送当前问题。
7. 识别发送后新出现的当前回答区域。
8. 等待回答开始生成、生成结束且正文连续稳定。
9. 提取当前回答的页面可见正文、引用、正文链接和检索候选。
10. 保存普通模式证据、最终回答截图和运行信息。
11. 将结果交给现有结构化分析和指标链路。
12. 释放豆包 Web 执行权，处理下一条豆包 Web 任务。

问题发送后不得自动重新发送，避免产生无法区分的重复样本。只有在问题尚未发送时，系统才可以恢复浏览器启动或页面导航。

### 5. 普通模式硬性要求

- 豆包 Web 的每个问题都必须使用普通模式，不提供“深入研究”开关。
- 系统不得主动点击“深入研究”；若新会话存在唯一、明确的残留选中态，只允许点击一次将其关闭。
- 无法确认“深入研究”已关闭或页面状态与预期不一致时，当前问题必须失败且不得发送。
- 成功记录必须保留 `capture_mode.name = standard`、模式观测结果和对应截图证据。
- `web_capture.search.requested = false`；普通模式是否实际搜索以及展示哪些来源，以本次豆包回答的页面证据为准。网络观测取得检索候选时记录 `search.observed = true`，否则保留未知，不把未知误报为失败。

### 6. 回答完成与成功条件

一次豆包 Web 采集只有同时满足以下条件才算成功：

- 已确认当前问题使用新会话。
- 发送前已确认处于普通模式且“深入研究”未开启。
- 发送后识别到新的当前回答区域。
- 当前回答正文非空。
- 页面生成状态已经结束。
- 回答正文在规定时间内保持稳定。
- 最终回答截图保存成功。
- 采集结果通过字段、长度、协议和 URL 边界校验。

仅凭发送按钮恢复、停止生成按钮消失或页面短时间没有变化，不能单独证明回答已经完整。

任何必需条件失败时，不得将旧回答、加载中文本或部分回答作为成功结果。

### 7. 引用与链接口径

- 用户界面统一使用“引用”或“引用源”，避免使用容易造成来源归属误解的其他称呼。
- 只有当前回答正文中的引用标记、与当前回答关联的来源卡片或当前回答明确展示的来源链接，才计为平台引用。
- 仅出现在正文中的普通链接可以保存为回答正文链接，但不进入引用率与引用次数 KPI。
- 只出现在平台检索过程、且未被当前回答引用的来源保存为检索候选，不进入引用 KPI。
- 普通模式回答没有展示引用时，任务可以成功，引用数量记为 `0`。
- 引用只接受可校验的 HTTP/HTTPS 地址，并执行去重和安全规范化。
- 报告必须让用户区分平台引用、正文链接和检索候选。

### 8. 队列、并行与运行状态

- 所有 `doubao-web` 问题进入豆包 Web 独立的先进先出队列。
- 豆包 Web 同一时刻最多有一个问题处于页面交互或采集阶段。
- DeepSeek Web 使用自己的独立 FIFO 和浏览器实例。
- 资源允许时，豆包 Web 与 DeepSeek Web 可以同时各执行一个页面任务。
- 豆包 Web 不等待 DeepSeek Web 队列；DeepSeek Web 也不等待豆包 Web 队列。
- API 平台继续使用现有并发能力，不进入任一 Web 队列。
- 用户可以看到豆包 Web 的 `idle`、`busy`、`login_required`、`verification_required`、`unavailable` 和 `shutting_down` 状态。
- 忙碌状态展示当前仍可执行或已经取得执行权的豆包 Web 问题数量，不承诺精确 ETA。

### 9. 正式运行入口

- 豆包 Web 支持问题库单问题运行。
- 豆包 Web 支持问题集运行，并在独立运行报告中持续更新状态。
- 豆包 Web 支持从原运行报告重试失败项。
- 豆包 Web 支持项目自动监测。
- 单问题、问题集、重试和自动监测必须使用相同的豆包 Web 普通模式采集能力和错误语义。
- 用户关闭浏览器或离开报告页后，目标虚拟机中的已提交任务继续执行。
- 不再使用的旧独立检测入口不得意外调用豆包 Web。

### 10. 证据、分析、历史与删除

成功记录至少保留：

- 页面最终可见回答正文。
- 平台引用、正文链接和检索候选。
- 豆包会话页面地址。
- 采集开始、完成和截图时间。
- 采集规则版本和页面识别版本。
- 有界浏览器环境信息。
- 采集模式、模式观测状态，以及普通模式未主动请求搜索的事实。
- 回答完成判据和正文摘要哈希。
- 普通模式截图和最终回答截图的证据标识及文件哈希。

截图文件不直接写入数据库；数据库只保存不透明证据标识和有界运行信息，不向前端返回服务器绝对路径。

豆包 Web 原回答继续进入现有品牌、竞品、提及、推荐、排名、情绪和引用分析。Web 采集成功但结构化分析失败时，原回答、引用、截图和采集信息必须保留，并允许仅重做结构化分析，不重新访问豆包页面。

删除历史记录或永久删除项目时，对应豆包 Web 证据必须同步清理。证据访问继续遵守现有记录所有权和管理员权限。

### 11. 故障隔离与失败行为

豆包 Web 至少区分：

- Chrome 未配置或启动失败。
- 豆包专用 Profile 被占用。
- 尚未登录或登录失效。
- 页面需要人工验证或验证码。
- 页面结构与受支持版本不匹配。
- 新会话创建失败。
- 普通模式无法确认或残留“深入研究”无法关闭。
- 问题输入或发送失败。
- 回答开始或生成超时。
- 回答无法确认完整结束。
- 截图或证据保存失败。
- 浏览器意外关闭。

失败时：

- 当前记录保存稳定的错误阶段、错误码和用户可读说明。
- 不生成成功的 GEO 指标。
- 不把部分回答交给结构化分析。
- 不调用豆包 API，不生成 API 替代回答。
- 浏览器连接、命令或超时异常会回收豆包浏览器会话，后续任务重新启动。
- 登录、验证或选择器类故障使豆包 Web 进入不可用状态，并使其排队任务快速失败。
- 豆包 Web 故障不得直接改变 DeepSeek Web 的登录、队列或熔断状态。
- 错误提示不得包含账号、Token、Cookie、完整请求头、Profile 路径或原始敏感响应。

### 12. 分阶段启用

豆包 Web 初始状态必须为关闭。正式启用按以下顺序验收：

1. 在目标虚拟机中完成人工登录、服务重启和单问题试运行。
2. 验证有引用、无引用、长回答、生成超时和登录失效场景。
3. 验证问题集、失败重试、报告、历史和导出。
4. 验证项目自动监测。
5. 与 DeepSeek Web 同时运行，验证两个浏览器实例的隔离性和目标虚拟机资源稳定性。
6. 在目标 VM 由管理员主动启用后，验证登录提示、真实采集和故障恢复；管理员仍可按运行需要手工停用。

在第 6 步完成前，只能描述为“预置默认停用策略已生效、本地正式入口已验证”，不得声称目标 VM 的登录与运行环境已经验收。

## Acceptance Criteria

- AC-001: 系统中同时存在 `doubao` 和 `doubao-web`，平台名称、任务、历史和报告能够明确区分 API 与网页样本。
- AC-002: 新数据库初始化时 `doubao-web` 作为内置预置平台默认停用，必须由管理员主动启用；已有数据库继续保留管理员保存的启停状态，预置同步不得在重启时强行覆盖。
- AC-003: `doubao-web` 不要求 API Key，也不出现在模型目录、API 连接测试、结构化分析平台或问题建议平台中。
- AC-004: 虚拟机运维负责人可以从 `/admin/settings` 选择 `doubao-web` 并在专用 Chrome 中人工完成登录、账号切换或验证；统一 Web 登录命令仍作为备用入口。
- AC-005: 正常关闭登录浏览器并重启服务后，豆包专用 Profile 可以继续恢复已登录会话。
- AC-006: 豆包 Profile、浏览器实例和证据目录均不与 DeepSeek Web、日常 Chrome 或 SEO 浏览器共用。
- AC-007: 用户可以从问题库单问题入口选择豆包网页版并创建真实 Web 任务。
- AC-008: 问题集运行、失败重试和项目自动监测使用与单问题相同的豆包 Web 采集能力和错误语义。
- AC-009: 连续运行两个无关问题时，每个问题都建立新会话，第二个结果不包含第一个会话上下文。
- AC-010: 每次问题发送前系统都确认豆包普通模式，且不会主动开启“深入研究”；无法确认时任务失败且问题发送次数为 0。
- AC-011: 用户不能通过项目或问题配置开启豆包 Web 的“深入研究”模式。
- AC-012: 成功记录同时包含最终可见正文、普通模式证据、最终回答截图和完整的有界运行信息。
- AC-013: 成功条件同时验证新会话、新回答区域、正文非空、生成结束、正文稳定和截图成功。
- AC-014: 页面平台引用进入引用 KPI；普通正文链接和未被回答引用的检索候选不进入引用 KPI。
- AC-015: 普通模式回答没有展示引用时，任务仍可成功且引用数量为 `0`。
- AC-016: 产品界面和新需求文档统一使用“引用”或“引用源”，不得使用容易造成来源归属误解的其他用户可见名称。
- AC-017: 豆包 Web 原回答可以继续生成现有品牌提及、竞品、推荐、排名、情绪和引用分析。
- AC-018: Web 采集成功但结构化分析失败时，原回答、引用、截图和采集信息仍被保留，并支持仅重做分析。
- AC-019: 所有豆包 Web 页面任务在单个后端实例内严格串行，观测到的最大豆包页面采集并发数为 1。
- AC-020: 豆包 Web 与 DeepSeek Web 各自使用独立 FIFO，资源允许时可以同时各执行一个页面任务。
- AC-021: 豆包 Web 登录、验证、选择器或浏览器故障不会直接使 DeepSeek Web 进入相同故障状态。
- AC-022: API 平台不进入 Web FIFO，可以与豆包 Web 和 DeepSeek Web 并行运行。
- AC-023: 已登录用户可以看到豆包 Web 的空闲、忙碌、需要登录、需要验证、不可用和关闭中状态。
- AC-024: 忙碌状态展示豆包 Web 等待数量，但不展示无法保证的精确 ETA。
- AC-025: 登录失效、人工验证、页面结构变化、普通模式无法确认、生成超时和截图失败返回可区分的机器可读错误码。
- AC-026: 问题发送后系统不会自动再次提交；超时或回答不完整时记录失败，不把部分回答作为成功结果。
- AC-027: 任意豆包 Web 失败路径中豆包 API Adapter 调用次数为 0，系统不生成 API 替代回答。
- AC-028: 失败记录不创建成功的可见性指标，也不提供伪完整回答供结构化分析重试。
- AC-029: 系统不主动调用豆包网页未公开接口，不保存或重放 Authorization、Cookie 和完整请求头。
- AC-030: 数据库、日志、错误响应和证据元数据不包含账号密码、Authorization、Cookie 或浏览器 Profile 绝对路径。
- AC-031: 豆包 Web 截图通过不透明证据标识访问，记录所有者和管理员可以访问，其他用户被拒绝。
- AC-032: 删除普通历史记录或永久删除项目后，对应豆包 Web 证据被同步清理。
- AC-033: 历史、平台筛选、问题集报告、平台比较和导出始终保留 `doubao-web` 平台身份，不归一化到 `doubao`。
- AC-034: 目标虚拟机验收至少覆盖人工登录、服务重启、单问题、问题集、失败重试和项目自动监测。
- AC-035: 双 Web 验收证明豆包 Web 与 DeepSeek Web 可以同时运行，且两者账号、Profile、队列、会话、截图和故障状态互不混淆。
- AC-036: 实现验收通过正式用户入口、调用证据和代码搜索共同证明：`doubao-web` 实际走豆包网页采集路径，未调用豆包 API，也未重新启用任何旧兼容路径。
- AC-037: 设置页把 `doubao_web` 与 `deepseek_web` 都显示为“真实网页 · 专用 Chrome”，两者均不显示 API 请求参数、密钥、连接测试或 API 编辑操作。
- AC-038: 管理员可以查看浏览器、Profile、登录验证和最近验证状态，并执行打开专用 Chrome、切换账号、验证登录和刷新配置信息；“刷新配置信息”只读取浏览器配置、Profile 初始化状态和上次验证结果，不检查当前登录，接口不返回账号身份、凭据或 Profile 路径。
- AC-039: 千问 API 新预置默认包含 `search_options.forced_search = true` 且正式 Responses 请求添加 `web_search` 工具；DeepSeek API 新预置默认关闭，且预置同步不覆盖管理员已保存的值。

## Metrics / Success

- 豆包 Web 成功记录的正文、普通模式状态、最终截图和运行信息完整率为 100%。
- 成功豆包 Web 记录中主动开启“深入研究”的次数为 0。
- `doubao` 与 `doubao-web` 的历史、报告和导出误合并数量为 0。
- 豆包 Web 单平台最大页面采集并发数始终为 1。
- 豆包 Web 与 DeepSeek Web 的账号、Profile、会话、证据和故障状态串扰数量为 0。
- 豆包 Web 失败后调用豆包 API 或生成替代回答的次数为 0。
- 无引用回答被误判为采集失败的次数为 0。
- 普通正文链接或检索候选被误计为平台引用的次数为 0。
- 账号密码、Authorization、Cookie 或 Profile 绝对路径进入代码、数据库、日志和证据元数据的次数为 0。
- 目标虚拟机完成单问题、问题集、重试、自动监测和双 Web 并行真实入口验收后，方可将平台状态改为正式启用。

## Constraints

- 已确认具备豆包 Web 使用许可；本 PRD 仅定义技术实现与产品行为，不重新讨论许可范围。
- 第一版运行在现有目标虚拟机、单后端实例和持续可用的图形桌面会话中。
- 豆包 Web 使用一个公司服务账号和一个持久 Chrome Profile。
- 豆包 Web 与 DeepSeek Web 分别单页面串行，但允许跨平台并行。
- 目标虚拟机不得休眠；远程桌面断开后图形会话仍需持续存在。
- 数据库、豆包 Profile 和豆包证据目录必须位于持久磁盘。
- 必须使用页面真实交互，页面可见内容和截图是最终采集依据。
- 不允许通过复制 Token、Cookie、调用未公开接口或 API 回退替代网页交互。
- 豆包页面结构可能变化；系统必须通过版本化页面识别规则和失败关闭策略保护数据可信度。
- 人工启用与真实运行验收分离：全新安装的全部平台预置默认停用；管理员主动启用后，任一目标机器仍须独立完成登录、浏览器和真实页面验收。
